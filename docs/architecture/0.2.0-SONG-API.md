# 0.2.0 곡 API와 cursor 계약

Phase 2의 서버 계약은 인증된 내부 사용자 ID를 유일한 owner 입력으로 사용한다. URL query나 JSON body에 임의의 `ownerId`가 있어도 소비하지 않는다. 미소유·없는 ID·삭제된 ID의 상세 및 변경 응답은 모두 `NOT_FOUND`로 같게 처리한다.

## Route

| method | route | 의미 |
| --- | --- | --- |
| `GET` | `/api/songs` | 검색·상태·정렬·cursor 목록과 필터 전체 개수 |
| `POST` | `/api/songs` | `requestId` 기반 멱등 생성 |
| `GET` | `/api/songs/:songId` | 활성 곡 상세와 현재 지원 여부가 표시된 집계 |
| `PATCH` | `/api/songs/:songId` | 제목·설명·작업 메모·상태 변경 |
| `DELETE` | `/api/songs/:songId` | 멱등 soft delete |
| `PUT` | `/api/songs/:songId/favorite` | 즐겨찾기 명령 |
| `PUT` | `/api/songs/:songId/pin` | 핀과 0 이상 순서 명령 |
| `PUT` | `/api/songs/:songId/color` | 고정 색상 또는 `null` 명령 |

변경 요청은 정확한 앱 origin을 요구한다. 모든 응답은 `no-store`이며 갱신된 세션 쿠키가 있으면 함께 전달한다.

## 생성 멱등성

클라이언트는 폼 시도 한 번에 UUID `requestId` 하나를 만들고 결과를 모를 때 같은 값을 재사용한다. DB는 `(owner_id, request_id)`를 `song_create_requests`에 한 번만 저장하고, 같은 요청이 동시에 들어와도 transaction advisory lock 뒤 원래 song을 반환한다. 재전송에서 body가 달라져도 첫 성공 결과를 바꾸지 않는다.

## 목록 query

- `search`: 앞뒤 공백을 제거한 최대 200자. 제목·설명·작업 메모에서 대소문자 없이 문자 그대로 찾으므로 `%`, `_`도 wildcard가 아니다.
- `status`: 승인된 7개 상태 중 하나.
- `sort`: `updated_desc`, `created_desc`, `created_asc`, `title_asc`, `favorite_first`.
- `limit`: 기본 20, 1~50.
- `cursor`: 응답의 불투명 문자열을 수정하지 않고 같은 정렬에만 재사용한다.

모든 정렬은 핀 여부와 `pin_order`를 먼저 적용하고, 각 정렬 키 뒤에 UUID tie-breaker를 둔다. cursor는 offset이 아니라 마지막 row의 핀·정렬 키와 PostgreSQL 마이크로초 시각을 담는 keyset cursor라 같은 시각·제목에서도 중복과 누락을 만들지 않는다. `totalCount`는 cursor 이전 전체 필터 결과 수다.

## 아직 지원하지 않는 값

각 카드의 `lyricCount`는 `0`이다. 상세의 `counts.lyrics`, `counts.prompts`, `counts.rhymes`는 각각 `{ value: 0, available: false }`라 실제로 조회한 빈 자료와 후속 버전 미지원 상태를 구분한다. 목록 `capabilities`도 가사 본문 검색과 연결 자료 필터를 `false`로 알린다.

## 오류

- 인증 없음·만료: `AUTH_REQUIRED` 또는 인증 세부 코드와 `401`
- origin 불일치: `FORBIDDEN`, `403`
- 필드·query·cursor 오류: `VALIDATION_FAILED`, `400`, 안전한 필드별 `issues`
- 미소유·없음·삭제됨: `NOT_FOUND`, `404`
- 의존성 장애: 본문이나 DB 메시지 없이 `DEPENDENCY_UNAVAILABLE`, `503`

DELETE 재호출과 미소유 요청은 존재 여부를 구별할 수 없도록 동일한 `200 { deleted: false }`를 반환한다.
