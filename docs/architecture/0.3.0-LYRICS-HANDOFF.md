# 0.3.0 가사 영역 인계 계약

0.2.0 곡 대시보드가 0.3.0의 가사 resource와 목록을 받을 때 지켜야 할 owner·집계·삭제 경계를 정의한다.

## 곡 관계와 소유권

- 곡 식별자는 `resources.id`의 UUID이며 `resources.type = 'song'`과 같은 ID의 `songs.resource_id`가 1:1로 존재한다.
- 가사는 독립 `resource`로 만들고 활성 곡을 가리키는 명시적 관계를 둔다.
- 관계 양쪽의 `owner_id`가 같아야 하며 DB foreign key 또는 trigger와 강제 RLS로 교차 owner 연결을 거부한다.
- client의 `owner_id`, 이메일, provider subject는 소유권 입력으로 사용하지 않는다. 인증 세션의 내부 user ID만 transaction-local `app.user_id`로 전달한다.

## 대시보드 응답과 집계

현재 `GET /api/songs/:songId`의 가사 응답은 다음과 같다.

```json
{
  "counts": {
    "lyrics": { "value": 0, "available": false }
  }
}
```

0.3.0에서 가사 schema와 owner 격리가 준비되면 `PostgresSongStore.getSong`의 같은 owner transaction 안에서 활성 가사만 집계하고 `available: true`로 전환한다. 삭제된 가사, 다른 owner 가사, 관계가 끊긴 가사는 세지 않는다. 곡 목록 카드의 `lyricCount`도 같은 조건의 집계를 사용해 상세 수치와 달라지지 않게 한다.

대시보드 가사 영역은 최소한 다음 상태를 구분한다.

- `available: false`: 아직 기능이 연결되지 않은 0.2.0 상태
- `available: true, value: 0`: 기능은 사용 가능하지만 가사가 없는 상태
- `available: true, value > 0`: owner 범위 활성 가사 목록
- 요청 실패: 기존 가사가 0개인 것처럼 숨기지 않는 재시도 상태

## soft delete

현재 `soft_delete_song(uuid)`는 인증 owner의 활성 곡 resource만 `deleted_at`으로 숨기며 실제 row를 제거하지 않는다. 0.3.0 migration은 곡과 함께 활성 소속 가사를 같은 transaction·삭제 작업 ID로 숨기도록 이 함수를 forward 확장한다.

- 해당 곡에 소속된 활성 가사만 함께 숨긴다.
- 독립 라임 노트·프롬프트 resource와 연결 관계의 원본은 삭제하지 않는다.
- 이미 삭제된 곡의 반복 DELETE는 `deleted: false`인 현재 멱등 계약을 유지한다.
- 복원 기능이 생길 때는 같은 삭제 작업으로 숨긴 가사만 함께 복원한다.
- hard delete나 migration down으로 사용자 자료를 제거하지 않는다.

## 안정 locator와 화면 인계

- 곡 대시보드 route: `/songs/:songId`
- 가사 영역 heading: `가사 작업 공간`
- 현재 빈 상태 heading: `아직 작성된 가사가 없어요`
- 집계 영역: `.count-grid`, 가사 panel: `.lyrics-empty`
- 첫 가사 CTA는 실제 0.3.0 route와 저장 흐름이 완성될 때만 interactive element로 바꾼다.

0.3.0은 PC·모바일에서 기존 곡 헤더, 목록 복귀 query, 작업 메모와 삭제 dialog의 의미를 유지하면서 가사 영역 내부만 실제 자료 상태로 확장한다.
