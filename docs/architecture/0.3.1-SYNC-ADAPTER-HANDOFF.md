# 0.3.1 → 0.4.0 동기화 어댑터 인계

2026-09-06 소스 기준 계약이다. [요구사항 추적표](./0.3.1-REQUIREMENTS-TRACEABILITY.md)와 [Phase 5 로컬 검증](../runbooks/0.3.1-phase5-local-validation.md)을 함께 읽는다. 아래 가사 기준선은 0.4.0 Phase 1에서 라임 노트에도 확장됐다.

## 재사용 가능한 범위

같은 owner의 여러 탭·기기에서 하나의 본문을 병합하는 구조다. 다른 사용자 공유·역할·presence 계약은 없다. 0.3.1 기준 이름과 저장 경로는 가사 전용이었지만 [0400 schema](../../packages/database/migrations/0400_rhyme_notes.sql)가 `sync_documents.resource_type`을 `lyrics | rhyme_note`로 일반화했고 [CollaborationStore.ensureDocument](../../apps/collaboration/src/store.ts)가 활성 subtype을 서버에서 판정한다. 다른 resource 종류까지 범용이라고 가정하면 안 된다.

[editor package 진입점](../../packages/editor/src/index.ts)은 `browser-sync`, `crdt`, `codemirror`, `revision-diff`를 export한다. `SyncStorage`는 [내부 모듈](../../packages/editor/src/sync-storage.ts)의 exported class지만 package 진입점에서는 재수출하지 않는다. collaboration의 `CollaborationStore`는 서버 모듈이며 브라우저 import 대상이 아니다. `server.ts`는 기동 코드와 HTTP/WS 경계를 제공하며 별도의 공개 서버 factory를 export하지 않는다.

## CodeMirror와 CRDT 본문

| 소스 | 공개 심볼과 현행 의미 |
|---|---|
| [codemirror.ts](../../packages/editor/src/codemirror.ts) | `EditorTextChange { from, to, insert }`, `EditorDocumentTransaction { changes, selection?, origin, composing }`. `origin`은 `user` 또는 `external`. `createCodeMirrorTextEditor`의 `onTransaction`으로 확정 변경을 전달한다. |
| [browser-sync.ts](../../packages/editor/src/browser-sync.ts) | `createBrowserLyricSync`와 같은 계약의 `createBrowserRhymeSync({ ownerId, resourceId, initialBody, onRemoteBody, onStateChange, onEditableChange?, onLegacyConflict? })`. `initialBody`는 현재 함수 내부에서 seed에 사용하지 않는다. 최초 seed의 소유자는 서버다. |
| [crdt.ts](../../packages/editor/src/crdt.ts) | `createLyricDocument`/`createRhymeDocument`, body·snapshot·update 함수와 `projectLyric`/`projectRhyme`. 원본은 모두 `Y.Text("body")`; snapshot은 `Y.encodeStateAsUpdate`다. projector는 관계형 제목과 LF로 정규화한 본문을 반환한다. |
| [실제 UI 연결](../../apps/web/src/components/lyric-editor.tsx) | local transaction을 `applyLocalTransaction`에 넘긴다. `onRemoteBody(body, changes?)`는 delta가 있으면 editor의 `applyTransaction`으로 적용한다. 외부 transaction은 undo history에 추가하지 않고 로컬 update로 재송신하지 않는다. |

`BrowserLyricSync.applyLocalTransaction(transaction): void`는 초기화 뒤 `origin === "user"`, `composing === false`, 변경이 있는 경우만 처리한다. 변경은 역방향 offset 순으로 하나의 Yjs transaction에 적용한다. CodeMirror가 조합 중 ChangeSet을 누적하고 composition 종료에 확정 transaction을 보낸다. `setComposing(boolean)`은 조합 중 원격 Yjs update를 보류했다가 종료 후 적용한다. 이 조합 순서를 소비 화면이 유지해야 한다.

본문과 제목·메모·상태 등 관계형 metadata의 저장 경로를 합치지 않는다. 서버 projector는 `lyrics.body`를 갱신하며 제목을 CRDT에서 만들지 않는다. [store 통합 테스트](../../apps/collaboration/src/store.integration.test.ts)는 동기화 시작 뒤 REST 본문 덮어쓰기를 `VERSION_CONFLICT`로 거부하면서 관계형 제목 수정은 허용함을 확인한다.

## 로컬 초안과 수명

[SyncStorage](../../packages/editor/src/sync-storage.ts)의 schema version은 `1`이다. 브라우저 DB 이름의 `sync-v2` 접미사와 Dexie schema version을 혼동하지 않는다.

| 항목 | 현재 계약 |
|---|---|
| 계정 범위 | DB 이름 `lyricscloud-draft-${SHA256(ownerId)}-sync-v2`. 해시는 이름 격리이며 서버 권한 검사를 대체하지 않는다. |
| `LocalDocument` | `{ resourceId, documentKey, snapshot: Uint8Array }`. documents의 resourceId와 documentKey는 각각 unique다. |
| `QueuedUpdate` | `{ updateId, documentKey, payload: Uint8Array }`. updates는 자동 증가 sequence, unique updateId, documentKey index를 사용한다. |
| `persist(document, update?)` | 하나의 Dexie `rw` transaction에서 기존 snapshot과 `Y.mergeUpdates` 후 put, 필요하면 queue put. 기존 resource의 documentKey가 달라지면 `SYNC_DOCUMENT_CHANGED`. |
| 로컬 변경 | 브라우저가 `crypto.randomUUID()`를 한 번 발급해 snapshot과 update를 함께 기록하고 직렬 전송한다. 원격 변경은 snapshot만 로컬에 보존한다. |
| 탭 통신 | owner prefix+documentKey BroadcastChannel로 local update를 전달한다. 서버 ACK의 책임은 IndexedDB queue에 남는다. |
| 초기 복구 | cached snapshot을 적용한 뒤 서버 snapshot을 병합한다. cache가 없으면 서버 snapshot까지 편집 불가. legacy y-indexeddb 초안이 서버와 다르면 `onLegacyConflict`와 `conflict`로 중단한다. |
| 정리 | `clearOwnerLocalDrafts(ownerId): Promise<void>`가 owner channel에 clear를 방송하고 해당 prefix의 DB만 삭제한다. [clearAccountCache](../../apps/web/src/lib/account-cache.ts)는 local/sessionStorage 정리와 이를 결합한다. |

`destroy(): Promise<void>`는 abort·timer·socket·channel·event listener를 닫고 현재 writes를 기다린 후 storage와 Y.Doc을 닫는다. 미전송 큐 자체를 삭제하지 않는다. 계정 clear 방송이나 DB versionchange는 `unavailable`로 중단하고 destroy한다. 다른 계정의 새 화면은 `clearOtherOwnerLocalDrafts`로 이전 계정 초안을 정리한다. 같은 계정의 세션 만료는 삭제와 구분하며 초안을 남긴다. 탈퇴는 후속 버전 범위다.

`retry(): void`는 연결 backoff를 초기화한다. `error`에서는 메모리의 Yjs snapshot을 새 update로 다시 보존한다. `unavailable`에서는 재로그인 후 bootstrap을 다시 요청하며 서버가 owner·문서·삭제 상태를 재검증한다. `conflict`·destroyed는 재개하지 않는다. 연결 backoff는 500ms에서 최대 30s, ACK 유실 시 8s 후 연결을 닫고 **기존 durable update ID**를 재전송한다. 열린 앱의 offline 초안 복구와 네트워크 없는 cold start는 별개다.

`hasOwnerPendingDrafts`는 닫힌 탭까지 포함해 전송 대기열 유무를 확인한다. `readOwnerPendingDrafts`는 해당 자료의 로컬 snapshot 본문을 읽는 비상 보관용 경계다. 웹 `registerLogoutSave`는 현재 metadata·본문 저장과 메모리 초안 조회를 등록한다. `coordinateAccountLogout`은 탭별 shared Web Lock을 보유하고, 준비 방송 → 각 탭 입력 정지·저장 → exclusive lock → 전체 outbox 확인 → 서버 로그아웃 → 로컬 정리 순서를 지킨다. 준비/잠금 대기의 8초 제한을 넘기면 화면을 되돌린다. 개시 탭이 결과 방송 없이 닫히면 나머지 탭은 30초 뒤 shared lock을 다시 확보하고 입력을 재개한다. 살아 있는 로그아웃의 exclusive lock 중에는 재개하지 않는다. 삭제 등으로 전송할 수 없는 초안은 사용자가 내려받거나 복사한 뒤 명시적으로 삭제·로그아웃할 수 있다. 이는 일반 자료 내보내기나 백업 기능을 대신하지 않는다.

## 저장 상태의 보장 수준

소스: [LocalSyncState와 report/flush](../../packages/editor/src/browser-sync.ts), [SaveIndicator/LocalDraftIndicator](../../apps/web/src/components/lyric-editor.tsx). 상태는 해당 브라우저가 마지막으로 관측한 사실이다. 전 기기의 최신 상태나 모든 metadata 저장까지 보장하지 않는다.

| 상태 | 의미 |
|---|---|
| `loading` | 초기화 대기. 새 입력의 로컬·서버 저장 성공을 주장하지 않는다. |
| `saving-local` | IndexedDB writes가 남아 있다. 로컬 영속화 완료 전이다. |
| `local` | 초기화·로컬 writes 뒤 서버 연결 대기. 서버 ACK 보장 없음. |
| `offline` | 오프라인이며 로컬 writes 대기보다 낮은 우선순위로 표시된다. 서버 반영 보장 없음. |
| `syncing` | 연결되어 있고 문서 queue가 남아 있다. ACK를 기다리는 상태다. |
| `projection` | queue가 비었지만 마지막 서버 메시지가 projection pending이다. UI: “서버에 저장됨 · 검색 반영 중…”. |
| `ready` | 초기화·연결 완료, 로컬 writes/queue가 없고 관측한 projection pending이 없다. 관계형 `SaveState`와 함께 UI의 “방금 저장됨”을 결정한다. |
| `error` | 로컬/프로토콜 오류로 중단. 메모리 입력이 있어도 디스크 저장을 보장하지 않는다. 복사·재시도 안내. |
| `unavailable` | 로그인·owner·삭제 등 접근 불가로 중단. 로컬 입력을 자동 덮어쓰지 않는다. |
| `conflict` | legacy 본문 불일치 또는 documentKey 변경으로 자동 병합 중단. 수동 재시도로 우회하지 않는다. |

`flush(): Promise<boolean>`은 writes를 기다리고 `ready`를 기다린다(최대 8s). 중단·조합 중·오프라인·destroyed이면 false다. 단순 전송 시작이나 ACK 하나를 전체 저장 완료로 해석하지 않는다.

## owner 인증·전송·ACK·projection

[sync-contract.ts](../../packages/domain/src/sync-contract.ts)의 `SyncDocumentKey`, `SyncUpdateId`는 branded string이다. `authorizeSyncDocument`는 owner 불일치·미인증·만료·삭제를 `SYNC_DOCUMENT_UNAVAILABLE`로 반환한다. 실제 서버는 [server.ts](../../apps/collaboration/src/server.ts)의 session/Origin 검사와 store의 owner transaction/RLS를 사용한다. 클라이언트 ownerId를 인증 근거로 신뢰하지 않는다.

| 경로/메시지 | 현재 동작 |
|---|---|
| 브라우저 `POST /collaboration/documents/{resourceId}` | 서버 `POST /documents/{resourceId}`에 대응. `ensureDocument(ownerId, resourceId)`가 활성 owner 가사에 opaque `documentKey`를 반환한다. |
| 브라우저 WS `/collaboration/sync/{documentKey}` | 서버 `/sync/{documentKey}`에 대응. Origin·세션·owner 문서 확인 후 연결; `snapshot { payload, projection }` 수신. payload는 Base64 Yjs binary update다. |
| 송신 `update { updateId, payload }` | `parseSyncUpdateEnvelope`로 UUID 형태와 binary 1~1,048,576 bytes 검사. S.`applyUpdate`가 owner 범위 문서 lock 아래 처리한다. |
| 수신 `ack { updateId, duplicate, projection }` | DB transaction commit 뒤 발송. 브라우저는 `inFlight`와 같은 ID의 queue만 삭제한다. `projection`은 `pending` 또는 `current`. |
| 수신 `update { payload, updateId? }` | 다른 연결의 적용 완료 update 또는 복원 snapshot. 조합 중이면 보류한다. |
| 수신 `projection { projection }` | 재처리 완료 등을 알려 저장 상태를 갱신한다. |

`CollaborationStore`의 `ensureDocument`, `loadDocument`, `applyUpdate`, `retryProjection`, `listRevisions`, `getRevision`, `checkpoint`, `restoreRevision`은 ownerId를 받는다. 비공개 `#owned`가 transaction-local role과 owner context를 설정하고 commit/rollback한다. `loadDocument`는 `{ resourceId, resourceType, snapshot, updates, projectionPending }` 또는 null을 반환한다. `materialize(snapshot, updates)`는 복구용 Y.Doc을 만든다. projector는 저장된 `resourceType`에 따라 `lyrics.body` 또는 `rhyme_notes.body` 하나만 갱신한다.

`applyUpdate`는 `(documentKey, updateId)` receipt의 SHA-256을 비교한다. 같은 ID·같은 payload는 duplicate, 다른 payload는 `SYNC_UPDATE_ID_REUSED`다. receipt와 raw update를 보존한 뒤 평문 투영을 savepoint에서 시도한다. 투영 실패만 rollback하여 `SYNC_PROJECTION_FAILED` marker를 남길 수 있으므로 **durable ACK와 projection 성공은 별개**다. 100 raw updates 또는 합계 1MiB에서 snapshot을 압축하고 해당 raw rows를 제거하지만 receipt는 유지한다.

`retryPendingProjections(limit = 20)`은 marker 문서를 `retryProjection`으로 재처리한다. 서버는 5s마다 수행하고 성공 시 연결에 projection 상태를 알린다. `operationalMetrics()`는 documents·pendingProjections·maximumProjectionLagMs, 서버 metrics는 connections도 반환한다. lag는 `projected_at` 이후 시간의 최대값이며 순수 pending 처리시간과 동일한 척도가 아니다. 로그의 document는 축약 해시이고 제목·본문·payload를 기록하지 않는다. update latency와 retry 누적 카운터 전체가 이 API에 있는 것으로 쓰지 않는다.

접근 불가 WS는 4404, 프로토콜 오류는 4400, 일시 장애는 1013이다. HTTP 오류 body는 `SYNC_DOCUMENT_UNAVAILABLE`로 통일하지만 status는 401/403/404 등으로 구분된다. 서버는 수신 시 session, store에서 owner·삭제 상태를 검사하며 5분 주기 재인증도 한다. `SYNC_LIMITS.documentTextBytes = 400_000` 선언과 별개로 현행 store의 직접 본문 검사는 Unicode 문자 100,000개 상한이다.

## 수정 기록·비파괴 복원

소스: [revision-contract.ts](../../packages/domain/src/revision-contract.ts), [revisions.ts](../../apps/collaboration/src/revisions.ts), [store.ts](../../apps/collaboration/src/store.ts), [0311 schema](../../packages/database/migrations/0311_lyric_revisions.sql).

| 심볼 | 계약 |
|---|---|
| `REVISION_POLICY` | intervalMs 300000, retentionDays 180, maximumCount 200, largePasteCharacters 1000 |
| `RevisionSummary` / `LyricRevision` | id·createdAt·reason·preview·characters; 상세는 body 추가. preview는 최대 100 Unicode 문자. 명명된 가사 resource와 별도 ID·수명이다. |
| `RevisionHistory` | `{ current: { body, hash }, items }`. 현재 body/hash는 materialized CRDT 기준이다. |
| `RestoreRevisionInput` | `{ requestId, expectedHash }`; UUID와 64자리 소문자 hex hash를 검증한다. |
| `checkpoint(reason)` | 브라우저는 `leave`, `duplicate`, `large_paste`만 요청하며 먼저 flush한다. 서버 내부 `interval`과 `before_restore`는 외부 checkpoint 입력으로 허용하지 않는다. |
| `listRevisions()` / `getRevision(id)` | GET `/collaboration/documents/{documentKey}/revisions[/{id}]`. 접근 불가/오프라인 등은 예외이며 빈 성공 결과로 바꾸지 않는다. |
| `restoreRevision(id, input)` | flush 후 POST 같은 경로의 `/{id}/restore`. 응답 snapshot을 원격 update로 적용·로컬 보존하며 실패 시 예외. |

서버의 `maintainRevisions(limit = 20)`는 30s 주기 호출되며 5분이 지난 문서의 changed body만 `captureRevision`으로 기록한다. 연속 같은 hash는 기존 기록을 재사용하지만 `before_restore`는 새 기록을 남긴다. `pruneRevisions`는 180일 초과 또는 200개 초과를 제거한다. 복원 transaction에서 target과 직전 보존 ID를 개수 정리의 우선 대상으로 두되 이후 정상 보존 정책에서 무기한 제외하지 않는다.

복원은 문서 lock 안에서 현재 hash 비교 → 직전 본문 기록 → **기존 Y.Doc**의 본문 교체 → snapshot·평문·request receipt를 한 transaction으로 commit한다. projection 실패 시 복원 전체가 rollback된다. 이는 일반 update의 projection pending 처리와 다르다. 새 Y.Doc으로 바꾸지 않으므로 기존 오프라인 update는 기존 Yjs 식별자에 병합된다. 복원이 이후 오프라인 입력까지 영구히 무효화하는 계약은 아니다.

동일 requestId의 동일 revisionId+expectedHash 재시도는 복원을 재적용하지 않고 현재 snapshot을 돌려준다. ID 재사용 불일치는 `REVISION_REQUEST_REUSED`, 비교 이후 현재본 변경은 `REVISION_CURRENT_CHANGED`. HTTP는 입력 오류 400, 나머지 `REVISION_*` 오류 409를 반환한다. 브라우저 UI [LyricHistory](../../apps/web/src/components/lyric-history.tsx)는 불확실한 복원 응답 재시도에 같은 request를 보존한다. 새 요청을 만들어 무작정 반복하면 안 된다.

`checkpoint`는 이탈·복제·붙여넣기 전 성공을 기다리는 경로다. `leave(): void`는 pagehide/unmount 시 keepalive 요청을 보내는 최선 노력이며 flush를 기다리지 않는다. 종료 직전 미ACK 입력의 기록 생성은 보장하지 않고 IndexedDB queue가 복구 책임을 가진다. [compareRevisionLines](../../packages/editor/src/revision-diff.ts)는 줄 비교를 제공하며 timeout 150ms·maxEditLength 2000 초과 시 양쪽 원문을 보존한 단순 비교로 대체한다.

## ADR 차이와 미확인 인수 항목

[ADR-0005](../adr/ADR-0005-crdt-persistence.md)는 `y-codemirror.next` binding을 명시하지만 [현행 package](../../packages/editor/package.json)는 해당 의존성 없이 CodeMirror transaction↔Yjs adapter를 사용한다. 이번 인계는 현행 adapter를 유지하며 ADR 변경 승인이나 binding 교체 완료를 주장하지 않는다. ADR의 awareness 서술 역시 현재 owner 전용 본문 프로토콜에 구현된 presence API를 의미하지 않는다.

Phase 5의 실제 실행 결과는 [로컬 검증 기록](../runbooks/0.3.1-phase5-local-validation.md)을 따른다. 물리 기기/OS IME/다른 네트워크 인수는 사용자가 통과를 보고했고, 원격 CI·동일 SHA 개발 배포·공개 smoke 기록은 STATUS와 해당 검증 문서에 있다. 0.4.0 Phase 1은 라임 본문까지 이 인터페이스를 재사용했으며 prompt 등 다른 자료 종류까지 구현된 것으로 취급하지 않는다.
