# 0.2.0 owner context 인계

0.2.0의 resource·곡 생성 API는 0.1.0에서 확정한 내부 사용자 소유권 경계를 그대로 사용한다. client가 전달한 이메일, Google subject, `user_id`, `owner_id`는 소유권 입력이 아니다.

## 생성 명령 계약

1. route가 opaque session을 해석해 내부 `UserId`를 얻는다.
2. [`bindOwnerContext`](../../packages/domain/src/ownership.ts)는 인증 context가 없으면 `AUTH_CONTEXT_REQUIRED`로 중단한다.
3. client payload에 위조 `ownerId`가 있어도 제거하고 context의 `userId`를 결괏값에 넣는다.
4. repository는 transaction 안에서 `SET LOCAL ROLE lyricscloud_app`, transaction-local `app.user_id`를 설정한다.
5. table은 `owner_id` FK·owner 선두 index·강제 RLS의 `USING`과 `WITH CHECK`를 함께 가진다.
6. 재시도 가능한 생성 API는 owner context와 별도로 idempotency key를 요구한다.

```ts
const values = bindOwnerContext(
  { userId: authenticatedUser.id },
  { title: input.title }
);
await resources.create(authenticatedUser.id, values, idempotencyKey);
```

## 필수 회귀 묶음

- context 없음: 생성 거부
- body `ownerId=B`, session=A: A 소유로만 생성하거나 validation 거부
- B session으로 A UUID를 path·query·body에 전달: `NOT_FOUND`, A 자료 불변
- pool 재사용: commit·rollback 뒤 role과 `app.user_id` 초기화
- blocked 사용자: 읽기·생성 모두 기본 거부
- 동일 idempotency key 재시도: 자료 하나만 생성

합성 A/B UUID와 session은 [`tests/e2e/fixtures.ts`](../../tests/e2e/fixtures.ts)의 공개 테스트 전용 값만 사용한다. 실제 이메일·session·provider token을 fixture나 로그에 넣지 않는다.
