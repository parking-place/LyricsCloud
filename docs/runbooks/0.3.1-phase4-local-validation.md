# 0.3.1 Phase 4 로컬 구현·검증

2026-09-06, `codex/0.3.1-p4-revisions`, 기반 commit `010a974`.

사용자의 기능 개발 계속 지시에 따라 Phase 3의 검증된 로컬 동기화 위에서 수정 기록·비교·복원을 구현했다. **로컬 검증 상태는 review이며 원격 Phase 완료가 아니다.** Phase 3과 Phase 4의 원격 반영·CI·Docker Hub 발행·동일 SHA 개발 서버 배포는 수행하지 않았다.

## 구현과 사용자 동작

- 현재 가사 본문, 이름 있는 독립 가사 버전, 복구용 수정 기록을 구분한다. 기록은 가사 목록·개수에 포함되지 않는다. 제목·메모·즐겨찾기 등 관계형 metadata는 본문 복원으로 바뀌지 않는다.
- CRDT 원본에서 본문 hash를 계산한다. collaboration 서비스가 30초마다 소량의 대상 문서를 확인하고 문서별 5분 간격으로 변경된 본문만 기록한다. 같은 본문의 연속 기록은 합친다.
- 가사 전환·곡으로 돌아가기·복제는 동기화와 중요 기록의 성공을 기다린다. 1,000 Unicode 문자 이상의 붙여넣기는 기존 본문을 먼저 기록하며, 실패하면 본문을 유지하고 다시 붙여넣도록 안내한다.
- 브라우저의 페이지 종료·임의 탐색에는 `pagehide`/unmount의 keepalive 요청으로 서버에 확정된 상태를 기록한다. 브라우저 강제 종료나 오프라인에서는 이 HTTP 요청을 보장할 수 없다. 아직 ACK를 받지 못한 입력의 복구 책임은 기존 계정별 IndexedDB 전송 대기열에 남는다.
- 기록은 최대 180일·문서당 200개로 정리한다. 복원 작업 중에는 선택한 기록과 방금 생성한 복원 직전 기록을 우선 보존하면서 200개를 유지한다. 중요한 기록도 이후의 정상 보존 기간·개수 정책에서 무기한 제외되지는 않는다.
- PC는 두 본문을 나란히, 모바일은 위아래 또는 현재본/선택한 본문 전환으로 보여 준다. 줄 번호, 추가·삭제 기호, 빈 줄, 송폼, 끝줄 줄바꿈을 구분한다. 긴 전체 교체도 계산 한도 안에서 원문을 보존해 표시한다.
- 복원 확인 후 현재 본문을 새 immutable 기록으로 저장하고 기존 Yjs 문서에 선택한 본문을 적용한다. 새 문서로 바꾸지 않으므로 오프라인에서 기존 문서에 입력한 변경도 재연결 때 병합된다.
- 현재본 보존, CRDT snapshot, 평문 투영, 복원 요청 receipt는 한 DB transaction이다. 실패하면 전부 rollback된다. 비교 후 다른 기기에서 내용이 바뀌면 409로 거절하고 최신 본문을 다시 비교하게 한다. 응답을 잃고 재시도해도 같은 요청 ID로 이미 수행한 복원을 다시 적용하지 않는다.

모든 자동 테스트 자료는 별도 PostgreSQL `lyricscloud_test`의 합성 자료다. 실제 Google 계정이나 개인 가사를 fixture로 쓰지 않았다.

| 단위·DB 전체 | 30 files / 103 tests 통과; 기존 crash recovery 포함 |

| migration 복구 | 0311 신규 적용·반복·실제 기록이 있는 rollback 거절·현재본 보존·재적용 통과. 영향받는 0200·0300·0310 복구도 통과 |

증거는 Git에서 제외된 `.private/p4-*.log`와 `p4-revisions-desktop.png`, `p4-revisions-mobile.png`에 있다. Docker 이미지 검증은 `scripts/verify-production-images.sh`에서 `verify-production-revisions.mjs`를 실행하며 CI에도 연결했다. 원격 CI 실행 자체는 하지 않았다.

Windows Git Bash에서 Docker 검증 스크립트를 실행할 때는 MSYS 경로 변환을 끈다. 이를 생략한 최초 smoke는 `/var/lib/postgresql`을 Windows 경로로 변환해 실패했으며 앱 결함이 아니었다.

```powershell
$env:MSYS_NO_PATHCONV = '1'
& 'C:\Program Files\Git\bin\bash.exe' scripts/verify-production-images.sh local-p4
```

## 로컬 실행과 OAuth

- 앱: `http://localhost:8080`, 가사 편집 상단 **버전 비교**, 모바일 하단 **기록·비교**.
- Compose project: `lyricscloud-local`, 기본 Compose와 `.private/compose.local.yaml` 사용. 개발 이미지: `lyricscloud-local-dev:p4-revisions`, build ID: `phase4-local`.
- web·collaboration·worker·PostgreSQL이 healthy이고 migrate는 정상 종료하는 일회성 작업이다. 원래 사용자가 GUI로 띄운 다른 컨테이너와 DB volume은 유지했다.
- 기존 `.env`의 DB·세션 비밀 값을 보존하고 개인 Google OAuth client와 `.test_users`를 적용했다. `/api/auth/login`의 302와 `accounts.google.com` 연결을 확인했고, 사용자가 실제 Google 로그인 후 `/workspace` 진입 성공을 확인했다. 실제 Google 로그아웃과 물리 모바일 기기 로그인은 이 기록의 검증 범위가 아니다.
- 현재 신원 scope만 요청하는 앱에서는 Google Console 테스트 사용자 등록이 선택 사항이며 앱의 `.test_users`는 필수다. [설정 절차](./google-oauth-setup.md), [Google Testing 예외](https://support.google.com/cloud/answer/15549945?hl=en)
- 사용자가 본 hydration 경고의 `data-jvyycdlz`는 source와 서버의 `<html lang="ko">`에 없었다. 브라우저에서 추가된 속성으로 추정하며 확장 기능을 끈 창으로 원인을 좁힐 수 있다. 깨끗한 브라우저의 revision E2E에서는 hydration 오류가 없었다. 경고를 숨기는 코드 변경은 하지 않았다.

로컬 이미지 교체 후에는 열린 화면을 저장하고 새로고침하면 새 기능을 쓸 수 있다. 실행 소스는 이미지에 복사되므로 향후 코드 수정에는 개발 이미지 재빌드가 필요하다.

## 복구·다음 단계

새 migration은 기록 테이블과 보조 열만 추가한다. 기존 가사·CRDT를 삭제하지 않는다. 롤백 시 우선 이전 `lyricscloud-local-dev:p3-fixed` 이미지로 소프트웨어만 되돌리고 새 기록 schema는 보존한다. 기록이나 복원 receipt가 하나라도 있으면 0311 down migration은 거절한다. 이 제한을 우회하거나 사용자 기록을 삭제하지 않는다.

다음 계획은 Phase 5의 장애·계정 격리·인수 검증이다. Phase 3/4의 원격 push·CI·image 발행·개발 서버 배포는 별도 승인과 서버 정보가 필요하며, 이 로컬 검증을 공개 서버의 완료 증거로 대신하지 않는다. 물리 기기·OS IME·모바일 가상 키보드의 실제 수용과 앞서 인계한 ADR 정합성 항목도 구분해 처리한다.
