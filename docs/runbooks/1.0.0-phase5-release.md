## 불변 릴리스 순서

1. Phase 5 후보 commit에서 로컬 gate, 원격 CI, 네 signed 개발 image와 동일 SHA 개발 서버 공개 smoke를 통과한다.
2. 완료 상태를 담은 승인 commit도 같은 전체 gate와 exact-SHA 개발 배포를 통과한다.
3. 승인 commit에 annotated `v1.0.0` tag를 만들고 원격 tag object와 dereferenced commit을 비교한다. tag는 이동하지 않는다.
4. 정확한 tag ref에서 수동 CI를 `publish=true`, `release=true`로 실행한다.
5. 네 repository의 `1.0.0`, 전체 SHA, `Release`, `latest`가 서비스별 같은 digest인지 확인하고 cosign signature·provenance·SBOM을 검증한다.
6. production checkout을 tag commit에 detach하고 네 exact digest를 pull한다. migration one-shot 성공 후 application-first rolling 교체를 수행한다.
7. 공개 live/ready, 인증 차단, OAuth 시작, 합성 핵심 흐름, PWA, owner 격리, 실패 canary 제거와 안정 구간을 확인한다.
8. GitHub Release에 source SHA·CI run·네 digest·schema·production smoke와 backup 예외를 기록한다.

`main`에는 직접 push하지 않는다. 정식 tag는 Phase branch의 승인 commit을 직접 가리키며, 이후 main 반영이 필요하면 별도 PR과 필수 검사를 사용한다.

## 초기 운영 인수와 rollback

| 역할 | 담당 |
|---|---|
| evidence author / 최초 대응 | Codex: SHA·digest·schema·health·합성 probe와 내용 없는 지표 대조 |
| repository owner / 최종 승인 | 사용자: 정식 tag·GitHub Release·P2/P3 인수 |
| operations acceptance / rollback 결정 | 사용자: production 지속·중단·application rollback 판단 |
| security/data review | 자동 gate와 Codex 검토: 인증·owner·migration·secret·본문 노출 차단 |

배포 직후 30회 집중 probe로 service-unavailable·autosave·search·purge와 DB 상태를 본다. backup 경보는 미설치로 활성화되지 않으므로 정상으로 해석하지 않는다. 오류·P0/P1·digest/schema 불일치가 있으면 공개 instance를 직전 승인 digest로 application-first rollback하고 volume과 schema는 유지한다. destructive down migration은 금지하며 필요하면 roll-forward 또는 새 빈 DB restore를 사용한다. 단, 현재는 실제 production backup이 없으므로 DB 손실 복구를 보장하지 않는다.
