# 1.0.8 P1 곡 사용자정렬 계약 인수

- 승인: 2026-09-11 사용자 1.0.14까지 전체 Phase와 버전별 정식 릴리스 실행 지시
- 출발점: v1.0.7 main/release `a7bf38c03c392475a8f9adea68c675471069d0e5`
- 현재 Phase: 설계-only. 아래 입력은 P2~P4의 실제 DB/API/browser와 동일 SHA 개발 인수 전까지 PASS가 아니다.

## 저장·정렬 계약

P2는 기존 `resources.pin_order` 및 `library_view_settings`와 분리된 owner+type order state, item rank, idempotency request 저장소를 migration `1002_song_manual_order.sql`로 추가한다. 내부 type은 기존 resource discriminator인 `song`이다. state의 row version은 순서 전체의 CAS token이고 item은 resource ID, 현재 pin group, signed bigint rank를 가진다. `(owner,type,resource)`는 한 행, `(owner,type,pin_group,rank)`는 유일해야 한다.

기존 곡은 현재 보이는 기본 순서인 핀 그룹, `pin_order`, 최근 수정, 안정 ID 순으로 각 그룹에 `1,048,576` 간격을 두어 backfill한다. 새 곡과 복제는 현재 핀 그룹 끝에 붙인다. soft delete는 item을 남겨 원래 위치를 보존하고 restore는 같은 rank를 재사용한다. hard purge만 cascade 삭제한다. 핀 변경은 `pin_order`의 기존 의미를 유지하면서 manual item을 새 그룹 끝으로 같은 transaction에서 옮긴다. 누락된 구버전 item은 조회/명령 전에 해당 그룹 끝에 보충한다.

`manual` 정렬은 핀 그룹 우선, manual rank, ID 순이다. 다른 정렬은 기존 `is_pinned`, `pin_order`, 선택 정렬, ID 순을 그대로 사용한다. rank는 내부 구현이고 API/UI에 노출하지 않는다. 인접 rank 사이 정수 공간이 없으면 현재 owner+song+pin group만 같은 안정 순서와 gap으로 다시 번호를 매긴 뒤 한 transaction에서 이동한다. P2는 일반 이동과 강제 재분배 fixture의 행 수·실행 시간을 따로 기록한다.

## 이동·API 계약

`POST /api/songs/order/moves` body는 정확히 아래 다섯 필드만 받는다.

```json
{
  "requestId": "uuid",
  "itemId": "uuid",
  "beforeId": "uuid-or-null",
  "afterId": "uuid-or-null",
  "expectedVersion": 0
}
```

client owner, rank, 전체 ID 배열, 검색/필터 값과 알 수 없는 필드는 받지 않는다. anchor 둘 다 null, 대상과 같은 anchor, 동일한 두 anchor는 400이다. 대상/anchor는 인증 owner의 active song이고 같은 핀 그룹이어야 한다. 다른 owner나 삭제된 ID는 존재 여부를 구분하지 않는 404이며 어느 순서도 바꾸지 않는다. 그룹 교차는 409 `PIN_GROUP_MISMATCH`다.

필터된 목록에서는 이동 뒤 보이는 이전 항목을 `afterId`, 다음 항목을 `beforeId`로 보낸다. `beforeId`가 있으면 대상 제거 후 전체 순서에서 그 항목 바로 앞에 삽입한다. 없으면 `afterId` 바로 뒤에 삽입한다. 둘 다 있으면 같은 그룹에서 after가 before보다 앞서야 한다. 따라서 전체 A-B-C-D-E, 필터 A-C-E에서 E를 C 앞으로 옮기는 요청은 A/B/E/C/D가 되고 숨은 B/D는 재순위·삭제되지 않는다.

서버는 owner+type advisory transaction lock, state expected version, active resource/anchor, 핀 그룹을 차례로 확인한다. 성공한 실제 이동만 order version을 1 올린다. 이미 같은 경계인 새 요청은 no-op 결과를 저장하되 version을 올리지 않는다. 동일 request ID와 동일 payload 재전송은 같은 결과와 version을 `replayed: true`로 반환하고, 다른 payload 재사용은 409 `REQUEST_REUSE_MISMATCH`다. 같은 expected version의 두 탭 이동은 먼저 lock을 얻은 하나만 성공하며 나머지는 409 `ORDER_VERSION_CONFLICT`와 최신 version을 받고 첫 페이지를 다시 읽는다.

GET `/api/songs?sort=manual`은 기존 목록 필드에 `orderVersion`과 manual-order capability를 더한다. cursor는 기존 query signature에 pin group, rank, stable ID, order version을 결합한다. query나 version이 다른 cursor는 409로 중단하며 UI는 누적 목록을 버리고 첫 페이지를 다시 읽는다. 페이지가 같은 version이면 중복/누락 없이 이어진다. 구버전 client의 기존 sort/cursor는 그대로 동작한다.

## 실패 우선 입력표

| 입력 | 먼저 확인할 실패 | P2~P4 기대 |
|---|---|---|
| updated 순서에서 C를 drag/버튼 이동 | UI만 이동·서버 순서 없음 | 성공 뒤 `manual` URL/화면, 새로고침 동일 순서 |
| 전체 A-B-C-D-E, 필터 A-C-E에서 E→C 앞 | 보이는 배열 전체 저장·B/D 유실 | A-B-E-C-D, 숨은 곡·핀 값 불변 |
| 첫 페이지 12개만 로드 후 끝 이동 | 미로드 ID 삭제·중복 paging | anchor command만 전송, 동일 version cursor 무중복 |
| 같은 version 두 탭·응답 역전 | last-write·이중 rank | 한 성공·한 409, 재조회 후 서버 순서 수렴 |
| 같은 request 재전송 | version/rank 두 번 변경 | 같은 결과 replay, version 한 번만 증가 |
| 다른 owner/deleted anchor | 존재 노출·교차 owner 변경 | indistinguishable 404, 양쪽 state/rank 불변 |
| pinned→unpinned 경계 drag | 암묵 pin 변경 | 409과 핀 먼저 변경 안내, `pin_order` 불변 |
| 이동 저장 500/network abort | 낙관 순서 고착 | 원래 배열/sort 복원, 같은 request ID 재시도 |
| soft delete/restore, hard purge | 위치 소실·고아 rank | restore 원위치, purge만 cascade |
| 반복 midpoint 소진 | bigint 충돌·전체 사용자 재작성 | 현재 owner/type/group만 bounded rebalance |

## 담당·호환·되돌림

| 영역 | P2/P3 담당 | 증거 |
|---|---|---|
| enum/body/cursor 계약 | `packages/domain/src/song-contract.ts`, package export | invalid/unknown/anchor/version 단위 fixture |
| schema/RLS/rank/CAS/idempotency | `packages/database/migrations/1002_song_manual_order.sql`, `packages/database/src/songs.ts` | fresh/repeat/upgrade/owner/concurrency/rebalance PostgreSQL fixture |
| 인증 API | `apps/web/src/app/api/songs/order/moves/route.ts`, 기존 song API 오류 경계 | 400/401/403/404/409/private no-store |
| 목록·drag·버튼/키보드 | `apps/web/src/components/song-list-screen.tsx`, `apps/web/src/app/styles.css` | PC/mobile/a11y/filter/paging/rollback E2E |
| 교차 회귀 | `tests/new-feature/1.0.8.contract.test.ts`, `tests/e2e/new-feature-1.0.8.spec.ts` | P2 실패-first와 P3/P4 실제 기능 경로 |

P2는 contract/schema/store/API와 실제 DB를, P3는 PC/mobile UI를, P4는 전체 PostgreSQL·Chromium·지원 엔진·재시작을 맡는다. 가사 본문, IME, copy, 보기 mode, 라임/프롬프트 순서, prompt 내부 token 순서는 변경하지 않는다. 실제 물리 기기를 수행하지 않으면 browser 자동화를 실기기 PASS로 기록하지 않는다.

application-first rollback은 이동 UI/API와 `manual` 선택을 숨기고 기존 `updated_desc` 목록으로 돌아간다. 새 table은 기존 자료를 변경하지 않아 남겨도 구버전 client에 영향이 없다. down migration은 order state/item/request만 제거하지만 개인 순서를 잃으므로 정식 환경에서는 별도 승인 없이 실행하지 않는다.
