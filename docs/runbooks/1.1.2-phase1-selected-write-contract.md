- 승인일: 2026-09-13

- 상태: 1.1.2 selected-user body write와 writer presence/cursor **Accepted**. public-link write와 비로그인 guest는 1.1.3 P1 전 비활성이다.

## 권한 집합과 관리 경계

1. owner는 계속 자료의 유일한 소유자다. 지정 writer는 가사 본문 CRDT update만 제출할 수 있고 제목·상태·메모·연결 자료·revision 복원·공유 ACL·휴지통·완전 삭제·소유권·계정 설정은 관리하지 못한다.
2. 쓰기는 별도 사용자를 임의로 추가하는 권한이 아니라 활성 `lyric_read_grants` 행의 제한된 상태다. `write_enabled=true`인 active·미만료 read grant만 W에 포함하므로 실제 사용자 집합에서 항상 W⊆R이다.
3. owner와 동일 사용자를 grant할 수 없고, R={owner,A}, W={owner,B}처럼 B에게 활성 read grant가 없는 요청은 한 transaction에서 거부하며 기존 ACL을 바꾸지 않는다.
4. 기존 read grant는 기본 `write_enabled=false`다. owner만 읽기→쓰기 승격과 쓰기→읽기 강등을 요청할 수 있다. writer는 자기 grant·다른 사용자의 grant·공개 링크 설정을 변경할 수 없다.
5. reader가 탈퇴·만료·read 회수되면 write도 즉시 사라진다. write만 회수하면 read와 읽기 presence는 유지하고 편집·cursor 송신만 중단한다.

## 저장과 epoch

- `lyric_read_grants`에 `write_enabled`, 양의 `write_epoch`, 변경 시각을 추가한다. 별도 독립 writer 행은 만들지 않는다. active read grant의 `id`, 기존 `permission_epoch`, 새 `write_epoch` 세 값을 하나의 쓰기 capability tuple로 사용한다.
- read 회수·재발급은 기존 `permission_epoch`/새 grant ID 경계다. write 승격·강등은 같은 grant의 `write_epoch`를 항상 증가시킨다. 강등 뒤 재승격돼도 과거 epoch의 update는 다시 유효해지지 않는다.
- owner mode에는 grant tuple이 없다. selected writer update에는 서버가 인증 세션에서 얻은 `actor_id`와 현재 grant tuple을 결합하며 body가 주장한 owner·actor는 받지 않는다.
- `sync_updates`와 `sync_update_receipts`는 내부 `actor_id`, access 종류, grant ID와 두 epoch를 기록한다. `sync_documents`는 최근 accepted actor를 가리킬 수 있고 revision attribution은 내부 actor와 공개용 안전한 표시 이름만 연결한다. 이메일·원문·cursor는 로그에 남기지 않는다.
- 1.1.1 이전 update/receipt는 owner update로 해석하는 additive migration을 사용한다. 기존 Yjs document key·snapshot·update payload·평문 projection·revision 본문 형식은 바꾸지 않는다.

## 원자 update·ACK·경쟁 규칙

1. writer가 보내는 update envelope은 `updateId`, Yjs payload, `grantId`, `permissionEpoch`, `writeEpoch`를 포함한다. 서버는 매 WebSocket message마다 세션 actor를 다시 확인한다.
2. DB transaction은 document advisory lock과 대상 grant row lock을 잡고 active read, 미만료, `write_enabled`, actor·resource·owner·grant ID와 두 epoch를 모두 검사한 뒤 receipt·update·평문 projection·최근 actor를 함께 commit한다.
3. ACK는 commit 뒤에만 보낸다. `updateId`, duplicate 여부, accepted server sequence, 현재 두 epoch와 projection 상태를 포함한다. 연결이 commit 뒤 ACK 전에 끊기면 동일 ID·동일 hash 재전송은 같은 receipt를 반환하고, 같은 ID·다른 hash는 거부한다.
4. update transaction이 먼저 grant lock을 얻어 commit하면 그 update까지 승인되고 ACK 대상이다. 강등/회수 transaction이 먼저 commit하면 해당 epoch update와 그 이후 재시도는 거부된다. 클라이언트 시각이나 socket 도착 시각으로 경계를 추측하지 않는다.
5. accepted update만 다른 참가자에게 broadcast한다. 거부 update는 projection·revision·search·copy 결과에 들어가지 않고 다른 참가자에게 전송되지 않는다.

## 편집·undo·오프라인 복구

- writer는 기존 한글 IME와 Yjs document를 그대로 사용한다. 조합 중간값은 update로 확정하지 않고 composition 종료 transaction만 local origin으로 기록한다.
- undo/redo는 해당 탭의 local origin만 추적한다. 상대 writer·owner의 remote update나 server snapshot을 자기 undo로 제거하지 않는다. selection은 Yjs relative position으로 유지한다.
- 전송 전 update는 계정+actor+resource+grant ID+write epoch로 격리해 IndexedDB에 보관한다. ACK를 받은 update만 정상 queue에서 삭제한다.
- write 강등·read 회수·만료 응답을 받으면 자동 재전송을 즉시 멈추고 해당 epoch queue를 `rejected` 복구함으로 이동한다. 서버 snapshot에 다시 합치거나 재승격 뒤 자동 적용하지 않는다.
- 복구함은 권한을 잃기 직전 합법적으로 보던 working copy와 본인 local update를 기기에만 보존하며 복사·다운로드·폐기를 제공한다. 회수 뒤 서버의 새 본문·presence·revision을 읽지 않는다. 새 권한을 받아도 사용자가 현재 서버본을 확인하고 새 local transaction으로 명시 적용하기 전에는 전송하지 않는다.

## presence·cursor·selection

- 인증된 owner·selected reader·selected writer만 같은 문서의 presence를 받는다. public-link reader는 계속 identity presence를 주고받지 않는다.
- identity는 서버 세션이 결합한 안전한 표시 이름, connection-local 무작위 `participantId`, `role=owner|write|read`, ephemeral palette color만 제공한다. 이메일·내부 user ID·sharing ID·다른 문서 정보는 노출하지 않는다.
- writer만 `awareness` frame으로 Yjs relative anchor/head와 `active|idle` 상태를 보낼 수 있다. body·선택 문자열·identity는 받지 않으며 frame 크기·빈도·유효 문서 범위를 제한한다. reader는 참가 여부만 표시하고 편집 cursor처럼 보이지 않는다.
- 같은 계정의 여러 탭은 서로 다른 participant로 보되 같은 안전한 표시 이름으로 묶을 수 있다. 자기 caret와 remote caret를 중복 렌더링하지 않는다. disconnect·heartbeat timeout·문서 전환·read 회수는 presence와 selection을 즉시 제거한다.
- write만 강등되면 같은 연결을 read로 낮추고 remote 본문·participant 목록은 계속 받되 자기 selection 송신을 중단하고 기존 cursor를 제거한다. idle·지연·재연결 상태는 색만이 아니라 텍스트로 알린다.

## API·화면 인터페이스

- 기존 owner grant 목록 응답은 `access: "read"|"write"`, `permissionEpoch`, `writeEpoch`를 제공한다. 기존 1.1.1 클라이언트가 모르는 추가 필드는 무시할 수 있다.
- owner는 `PATCH /api/lyrics/:lyricId/shares/:grantId`에 `{ requestId, access }`를 보내 승격·강등한다. request ID는 owner+resource+grant에 멱등이며 다른 payload 재사용은 409다. inactive/foreign/missing 대상은 일반 404다.
- shared lyric 응답은 현재 access와 epoch tuple만 추가하고 memo·연결 자료·revision·owner 관리 API는 계속 제외한다. writer 화면은 본문 편집기, 권한·저장·연결 상태, 참가자/cursor와 복구함 동작만 제공한다.
- 권한이 read로 바뀌면 화면을 닫지 않고 읽기 전용으로 전환한다. read까지 사라지면 일반 unavailable 화면으로 전환하고 마지막 미전송 원문은 복구함에서만 제공한다.

## 호환·되돌림·파일 담당

- 기능 flag를 끄면 모든 selected grant를 read-only로 취급하고 writer update/awareness를 거부하되 새 column·audit·복구함과 원문은 보존한다. 애플리케이션을 1.1.1로 먼저 rollback할 수 있다.

## 미실행과 P2 인계

P1은 설계-only라 runtime, migration, CI, 서버 배포를 실행하지 않았다. P2는 additive `1120_selected_lyric_write.sql`과 rollback, owner grant access API, actor/epoch를 원자 검사하는 update store·ACK와 local rejected queue의 실패 시험부터 시작한다. P3는 owner 관리와 writer PC/mobile 편집·presence/cursor·복구함을 연결하고 P4는 실제 PostgreSQL 경쟁·지원 브라우저·서비스 재시작·두 실제 계정/기기·권한 회귀를 담당한다. 실제 OS/물리 기기와 `OPS-100-001` 예외는 미실행 위험으로 유지한다.
