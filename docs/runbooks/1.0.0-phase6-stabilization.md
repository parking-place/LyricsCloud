- 신규 라임·프롬프트는 계정별 여러 IndexedDB row와 Web Locks로 활성 탭을 분리한다. 기존 `new` row와 닫힌 탭의 초안을 복구하며, PWA·로그아웃 검사와 초안 내보내기는 모든 row를 포함한다.
- 전송한 생성 payload와 요청 ID를 유지한다. 결과 불명 상태에서는 입력을 잠그고 같은 요청의 결과를 회수한다. 라임·프롬프트는 전송 내용을 먼저 영속 저장하여 재진입 후에도 같은 요청을 재시도한다. 명확한 입력/권한 오류는 입력 수정을 다시 허용한다.
- 취소·이탈 후 생성 타이머/응답이 재이동하거나 초안을 다시 쓰지 못하게 한다. 취소는 이 기기의 초안 폐기이며, 취소 직전에 서버가 이미 생성한 문서를 원격 삭제하지 않는다.
- 프롬프트의 템플릿 최초 적용과 로컬 복구를 분리한다. 템플릿 재조회 실패로 복구 내용을 빈 상태로 덮어쓰지 않는다. 가사·템플릿 전송 중 입력과 대상 변경을 제한한다.
- PWA는 신규 가사/라임/프롬프트·템플릿 폼·미추가 토큰 입력과 조합 상태를 검사한다. worker 활성화 중 생긴 입력도 새로고침 직전에 재검사하며, 입력 보존 후 사용자가 다시 적용할 수 있다.

### 로컬 Docker 운영

Compose project `lyricscloud-local`에 postgres, web, collaboration, worker, migrate를 묶는다. migrate는 성공 후 종료하는 일회성 작업이며 나머지 네 서비스가 정상 실행 상태다. 기존 PostgreSQL 볼륨과 OAuth 설정은 보존한다. 갱신 전 pg_dump custom archive를 비공개 로컬 경로에 보관하고 목록 판독을 확인했다. 실제 복원 성공 증거로 확대하지 않는다.

로컬 이미지는 `parkingplace/lyricscloud-<service>:p6-local-<SHA>`로 구분하며 Docker Hub 공용 tag를 이동하지 않는다. 임시 테스트 컨테이너/네트워크와 이전 미사용 LyricsCloud 이미지는 새 서비스 확인 후 정리한다. 사용자의 5개 서비스 그룹 유지 요청에 따라 성공한 migrate 컨테이너는 그룹에 남기며 볼륨 prune을 실행하지 않는다. 되돌림은 새 앱을 중지하고 보존한 이전 이미지/설정을 사용한다. DB 되돌림이 필요하면 원본 볼륨을 덮어쓰지 않고 백업을 별도 복구 볼륨에 복원한 뒤 검증한다.

PC의 기존 `http://localhost:8080` OAuth 클라이언트를 유지하기 위해 비공개 Compose override의 web만 `Dockerfile.web` build stage와 `pnpm --filter @lyricscloud/web dev`를 사용한다. 나머지 앱은 production runtime을 사용한다. production에서 실제 Google OAuth는 HTTPS가 필수이므로 보안 검사를 완화하거나 OIDC test fixture로 우회하지 않는다. 공용 self-host 배포에는 이 로컬 override를 사용하지 않는다.

로컬 확인: 네 상시 서비스 healthy, migrate exit 0, schema `0802_lifecycle.sql`, live/ready/auth 및 정적 asset HTTP 200, Google 로그인 시작 HTTP 302와 Google 목적지 확인. 실제 사용자 로그인 완료는 사용자가 기존 브라우저에서 진행한다. PostgreSQL 원본 볼륨과 OAuth 파일을 유지했고 임시 컨테이너·테스트 네트워크·이전 미사용 이미지·미사용 build cache를 정리했다. rollback용 이전 로컬 P5 이미지는 하나 보존했다.

### CI 후속 관측

코드 수정 SHA `3cce95366904fd1576d63feb7916a1a846b1beb1`의 첫 push/PR 실행에서 P6 회귀·전체 tracked 구문 검사·dependency audit·secret scan·migration·typecheck·unit·production build는 통과했다. 성능 검사의 latency budget은 모두 통과하고 오류율도 0이었으나, push는 revision(전체 p95 2.538ms), PR은 save(전체 p95 4.149ms)의 3회 측정 편차가 75% 기준을 초과했다. 이 측정 코드와 예산은 이번 수정에서 변경하지 않았다. 서로 다른 지점의 실행 편차로 보고 기준을 그대로 둔 1회 재실행을 요청했다. 정확한 최종 후보 CI 결론과 실행 링크는 Draft PR #11에 기록한다. 성능 편차 실패 이력은 삭제하거나 성공으로 바꾸지 않는다.

## 제한된 최적화 측정

관측성에서 allowlist에 없는 필드의 중첩 객체 순회를 생략하고 금칙어 배열의 반복 할당·소문자 변환을 제거했다. 정상/민감/이상 입력 1,003개에서 이전 수정본과 결과가 같았다. 첫 100개 top-level 필드 제한과 redaction 깊이 제한을 유지한다.

동일 프로세스 5회 교대 측정, 회당 10,000회, 1,000회 warm-up의 중앙값:

| 합성 입력 | 이전 ms | 이후 ms |
|---|---:|---:|
| 일반 route 오류 로그 | 136.268 | 73.904 |
| 일반 저장 metric | 98.968 | 50.190 |

이 수치는 Node 22의 함수 미세 측정이다. 전체 앱·Node 24 production·사용자 체감·p95 개선으로 확대 해석하지 않는다. 알려지지 않은 중첩 객체의 극단 합성 시험은 더 큰 차이가 있었지만 제품 성능 배수로 사용하지 않는다.

## 원본과 릴리스 보존

STATUS 과거 전체 blob은 같은 디렉터리의 `STATUS-1.0.0-P5.md`로 손실 없이 보존한다. 기존 Phase 5 validator는 P5 기록 검사를 유지하면서 P6 상태를 별도로 검증한다. `--require-release`는 P6를 허용하지 않는다. 다른 개발 브랜치의 기존 발행 계약은 이번 P6 전용 수정에서 바꾸지 않는다.

## 미완료와 인수 조건

REVIEW-01~05·07·10의 위 재현 시나리오는 수정했지만 실제 OS IME·기기 인수, Yjs 경고, 전체 의미 기반 코드 리뷰·React Hooks·장시간 성능·의존성 최신화 판정은 미완료다. 과거 PowerShell 계획 검사기는 고정 5-phase와 잘못된 current_phase 해석 등 기존 한계가 있어 P6 문서까지 검증했다고 주장하지 않는다. 전체 CI 결과 없이 Phase 성공을 선언하거나 테스트를 삭제/완화하지 않는다.

projection 실패 시 export는 보수적으로 503을 반환한다. 특히 휴지통 문서의 pending projection도 영향을 줄 수 있으므로 복구 가용성과 정확한 사용자 재시도 안내는 후속 작업이다. 백업 전체 checksum 검사는 archive I/O 비용이 있고 정상 backup/restore·운영 RPO 보장과 구분한다. 운영 백업 미구축 `OPS-100-001`은 이 코드 변경으로 닫히지 않는다.
