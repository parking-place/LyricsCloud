# OPS-0001 — RC 기능 동결과 변경 승인

## 결정

- ID와 상태: `OPS-0001` / `Accepted`
- 결정 Phase와 승인자: 0.9.1 Phase 1 / repository owner가 정책 승인자, Codex가 검증 증거 작성자
- 결정 시각: 2026-09-08 10:40 KST
- 범위: 0.9.1 RC branch, 후보 tag, 허용 변경, 회귀·추적·승인과 1.0 tag 발행
- 범위 밖: 신규 제품 기능, UI 재설계, main 직접 반영, 현재 요청에서 명시되지 않은 release server 변경

## 선택과 이유

Phase별 변경 집합은 `phase/0.9.1-p<phase>-<slug>`와 `phase/1.0.0-p<phase>-<slug>` branch에 격리한다. RC 후보 tag는 `v1.0.0-rc.<n>`, 정식 tag는 `v1.0.0` 형식이며 tag 대상은 CI·네 image 발행·개발 서버 동일 SHA smoke가 모두 통과한 commit 하나다. branch 이름이나 이동식 tag가 승인된 digest를 대신하지 않는다.

0.9.1 진입 뒤 허용되는 변경은 다음 네 종류뿐이다.

1. 재현된 결함 수정
2. 보안·데이터 보호 하드닝
3. 승인 budget을 맞추는 성능·안정성 수정
4. 실제 동작·운영 절차를 정확히 만드는 테스트·문서 수정

새 기능, 승인되지 않은 dependency 대규모 갱신, schema 의미 변경, 디자인 재구성은 1.0.1 이후 backlog로 보낸다. P0/P1 수정에 schema나 의존성 변경이 불가피하면 release owner가 영향·rollback·추가 회귀를 승인한 뒤 별도 commit으로 수행한다.

## 변경 승인 절차

모든 RC 변경은 아래 순서를 만족해야 한다.

1. 결함/위험 ID, 등급, 재현, 영향 화면·API·schema를 기록한다.
2. §49/목업 추적 행과 알려진 제한 목록을 갱신한다.
3. 정상·빈·오류·권한 없음·모바일 중 영향 범위와 직접 회귀를 추가한다.
4. 로컬 수용 테스트를 통과한 commit을 Phase branch에 push한다.
5. 같은 SHA의 필수 CI와 web/collaboration/worker/migrate image 발행을 확인한다.
6. 같은 SHA를 개발 서버에 배포해 migration·health·공개 HTTPS smoke를 통과시킨다.
7. repository owner가 P0/P1 0건과 증거를 승인한 뒤 다음 Phase 또는 RC tag로 이동한다.

검증 실패를 재실행만으로 숨기지 않는다. flaky 원인을 별도 결함으로 기록하며, test 삭제·완화·범위 축소는 수정으로 인정하지 않는다.

## 역할과 태그 발행

| 역할 | 책임 |
|---|---|
| Evidence author | 구현·테스트·문서·digest·배포 증거 수집 |
| Security/Data owner | 인증·소유권·migration·backup 차단 판정 |
| Release owner | 변경 허용 여부, P2/P3 인수, RC 후보 승인 |
| Repository owner | 정식 `v1.0.0`과 운영 인수 최종 승인 |

`v1.0.0`은 1.0.0 Phase 1~4가 완료되고, 사용자가 현재 요청에서 정식 릴리즈와 release server 변경을 명시적으로 승인한 경우에만 발행한다. 승인 commit에 annotated/signature-capable tag를 만들고 GitHub release notes를 발행한 뒤 수동 release workflow를 `release=true`로 실행한다. `Release`와 `latest`는 네 version/SHA image와 같은 digest여야 하며 발행 뒤 같은 버전 image를 교체하지 않는다.

## 철회와 변경 비용

RC 승인은 새 P0/P1, source/digest 불일치, migration/restore 실패, secret·창작물 노출이 발견되면 자동 철회된다. 해당 Phase 이전의 검증된 개발 digest를 유지하고 수정 SHA에서 전체 gate를 처음부터 다시 수행한다. 이미 발행된 후보 tag는 이동하지 않고 다음 `rc.<n+1>`을 만든다.
