# 0.7.0 Phase 5 탐색 통합·릴리즈 검증

## 구현·통합 범위

- [0.7.0 탐색 기능 증적과 0.8.0 인계](../architecture/0.7.0-NAVIGATION-HANDOFF.md)에 Phase 1~5의 43개 작업 ID를 구현·테스트 증적과 연결했다.
- 검색 → 가사 Hook → 편집 → 최근 작업 → 저장된 cursor 복귀와, 핀·즐겨찾기 → 네 filter URL → 별도 모바일 기기 복원을 자동화했다.
- 두 owner와 soft-deleted 곡·가사를 검색·최근·saved API 전체에서 함께 회귀했다.
- PC·모바일 검색 loading·empty·error·retry와 최근·즐겨찾기 empty 화면을 screenshot 기준으로 고정했다.
- 빈 DB와 0.6.0 DB의 0700~0702 적용, 원문·owner·favorite·pin 보존 및 여섯 검색 index를 검사하는 release migration 스크립트를 추가했다.

## 성능 기준

개발 test DB 컨테이너에서 한 차례 warm-up 뒤 7회 측정한 median과 최댓값에 해당하는 보수적 p95다. 운영 SLO가 아니라 이후 회귀 비교 기준이다.

| 흐름 | 결과 수 | median | p95 |
|---|---:|---:|---:|
| `needle0700` 통합 검색 | 6 | 19.272 ms | 40.319 ms |
| 최근 작업 `limit=50` | 50 | 9.076 ms | 11.206 ms |
| saved 전체 목록 | 480 | 11.536 ms | 13.466 ms |

`EXPLAIN ANALYZE` anchor는 search 9.796ms, recent 0.786ms, saved 0.277ms였다. 작은 단일-owner 합성 분포에서는 planner가 sequential scan+sort/hash를 선택했다. 0700의 여섯 GIN index 존재는 release migration 검사로 별도 고정하며, 이 결과를 index 강제나 운영 SLO로 해석하지 않는다.

## migration 결론

- 신규 DB: 전체 migration 두 번 적용, current schema `0702_recent_items.sql`, recent 두 table과 검색 index 확인
- 이전 DB: 0000~`0501_prompt_usage.sql`만 적용해 0.6.0 fixture를 만든 뒤 현재 migrator를 두 번 실행
- 보존 확인: NFKC projection과 별개인 전각·공백 원문 제목, 줄바꿈 가사 본문, owner ID, favorite·pin·pin order
- 테스트 DB 두 개는 성공·실패와 무관하게 모든 pool을 먼저 닫고 일반 `drop database`로 제거한다. 강제 종료 경쟁 없이 기존 test DB나 Docker volume은 제거하지 않는다.
