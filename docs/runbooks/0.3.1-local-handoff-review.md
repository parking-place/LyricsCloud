검토는 `apps`, `packages`의 실행 소스와 호출 관계, SQL migration/rollback, Docker·Compose·CI·운영 스크립트, 단위·DB·브라우저 테스트를 대상으로 했다. 미래 기능의 정적 목업은 구현된 프로그램으로 세지 않았고, lockfile은 의존성 변경과 frozen install로 확인했다.

`apps/web`은 인증·화면·관계형 API, `apps/collaboration`은 같은 owner의 본문 동기화, `apps/worker`는 현재 health 프로세스다. `packages/domain`은 입력·소유권 계약, `database`는 SQL/RLS·저장, `auth`는 OIDC·세션, `editor`는 CodeMirror/Yjs·저장 어댑터를 담당한다. worker의 향후 정리·revision 작업이 이미 구현되었다고 판단하면 안 된다.

## Docker 실패 원인

1. worker/migrate의 `DATABASE_URL` 누락은 이미지를 개별 실행하면서 환경·PostgreSQL을 연결하지 않은 결과다. `.env`, IP, 운영 자격증명은 개발자가 의도적으로 제외한 인계 항목이며 소스 결함으로 분류하지 않았다.
2. collaboration의 `ERR_MODULE_NOT_FOUND: pg`는 직접 import하는 패키지를 운영 dependency에 선언하지 않은 결함이었다. 내려받은 배포 이미지 안에서 `--network none`으로도 재현했다. 루트 devDependency가 개발 설치에서는 이 결함을 가렸다.
3. 웹 이미지는 GUI에서 host 포트 없이 켜져 있었다. Compose로 DB·환경·포트·migration 순서를 함께 구성해야 한다. migrate는 성공 후 exit 0으로 종료되는 것이 정상이다.
4. 이 PC에는 개발용 Ubuntu 배포판 없이 `docker-desktop` WSL2만 있었다. 그래도 Linux 이미지의 Node/pnpm으로 설치·빌드·DB·브라우저 검증이 실행되었다. 개발용 Ubuntu 부재는 위 결함의 원인이 아니다. Docker 공식 설명도 Windows에서 별도 배포판 없이 사용할 수 있음을 명시한다: [Docker Desktop WSL](https://docs.docker.com/desktop/features/wsl/).

## Phase 3에서 보완한 내용

- collaboration의 운영 `pg` 의존성을 직접 선언했다. CI가 최종 네 이미지를 새 임시 PostgreSQL과 함께 실행하고, migration 완료·세 서비스 readiness·웹 경유 collaboration 경로를 확인한다.
- 브라우저는 같은 origin의 `/collaboration/documents/{resourceId}`로 opaque key를 얻고 `/collaboration/sync/{documentKey}` WebSocket에 연결한다. Next rewrite와 Caddy의 prefix 제거를 연결했다.
- 최초 본문 seed는 서버만 만든다. 브라우저가 기기마다 독립 seed를 삽입하거나, 빈 본문을 과거 서버 본문으로 되살리지 않는다.
- Dexie transaction 하나에 owner별 Yjs snapshot과 전송 대기 update를 저장한다. queue는 저장 순서대로 전송하며 서버 ACK 후 해당 ID만 제거한다. 연결 실패는 backoff로, ACK 유실은 같은 ID로 재전송한다. [Dexie transaction](https://dexie.org/docs/Dexie/Dexie.transaction())을 사용하며 IndexedDB transaction을 별도로 재구현하지 않았다.
- 기존 `y-indexeddb` 초안은 호환 읽기에 남겼다. 서버와 다른 과거 초안은 양쪽 내용을 보여주고 동기화를 중단하며 자동 덮어쓰지 않는다.
- 본문은 CRDT, 제목·메모·상태·즐겨찾기·핀은 기존 관계형 저장 경로로 나눴다. 본문 투영 때문에 바뀐 rowVersion은 metadata의 이전 값도 확인하며 재시도한다. CRDT가 시작된 가사의 REST 본문 덮어쓰기는 409로 거부한다.
- 기존 CodeMirror transaction adapter에서 한글 조합을 모아 확정 시 한 번 전달하고, 조합 중 원격 변경은 잠시 보류한다. 원격 변경은 delta로 적용해 커서를 불필요하게 초기화하지 않는다.
- 로컬 저장 중/완료, 서버 동기화 중, 서버 ACK와 검색 투영 지연을 구별한다. 최초 연결 동안은 본문을 읽기 전용으로 둔다.
- origin·세션·owner·삭제 상태를 확인하고, 수신하는 쪽의 취소된 세션도 방송 전에 차단한다. 최대 5분 간격 재인증과 일관된 snapshot 읽기를 추가했다.

## 로컬 검증 증거

- 수정 전 Linux 환경의 기존 단위·DB 검사 93개는 통과했지만, 저장소가 분리된 두 브라우저의 변경 전달 테스트는 실패했다. 환경 설정과 실제 누락을 분리한 기준이다.
- 수정 후 `pnpm check`, 단위·DB 96개 통과. 서버 프로세스를 update 처리 전, raw update insert 후 commit 전, commit 후 ACK 전에 실제 종료한 세 경우 모두 재시작·동일 ID 재전송으로 복구했다.
- PC·모바일 전체 E2E 86개를 한 번 실행해 84개 통과, 10만 자 편집 2개 실패를 확인했다. 초기 연결 대기와 FIFO queue를 보완한 뒤 해당 2개와 동기화 10개를 재검증해 통과했다. 변경과 무관한 성공 결과는 재사용했으며 마지막 상태에서 전체 86개를 다시 실행했다고 주장하지 않는다.
- 두 독립 브라우저, offline 편집 후 페이지 종료·복구, 빈 본문 유지, 합성 한글 composition, ACK 유실, IndexedDB transaction 실패와 수동 재시도를 확인했다. 모바일은 Chromium의 모바일 화면·터치 설정이며 실제 휴대전화/OS IME 검증은 별도다.
- 최종 운영 이미지에 개발 의존성을 추가로 설치하지 않고 migration exit 0, web/collaboration/worker readiness, 웹의 collaboration proxy를 확인했다. 재현 명령은 `bash scripts/verify-production-images.sh <image-tag>`이며 `lyricscloud-<service>-ci:<image-tag>` 네 이미지가 필요하다.
- 로그 원본은 로컬 `.private/p3-*.log`에 있다. 실제 Google 계정·운영 DB·개발자 서버는 사용하지 않았다. 실제 OAuth와 서로 다른 물리 기기의 네트워크 검증은 남아 있다.

## 이 PC에서 이어서 실행

`F:\LyricsCloud`의 `.env`와 `.test_users`는 Git에서 제외되어 있다. DB·세션 값은 로컬 전용으로 만들었고 Google 값은 채우지 않았다. 실제 로그인은 [Google OAuth 설정](./google-oauth-setup.md)에 따라 본인 개발용 client와 허용 이메일을 넣은 뒤 확인한다.

```powershell
docker compose -p lyricscloud-local -f compose.yaml -f .private/compose.local.yaml up -d --no-build --wait
docker compose -p lyricscloud-local -f compose.yaml -f .private/compose.local.yaml ps -a
```

웹은 [로컬 로그인 화면](http://localhost:8080/auth)이다. `.private/compose.local.yaml`은 Linux 의존성이 들어 있는 소스 snapshot 이미지를 쓰므로 코드 변경 후 이미지를 다시 빌드해야 한다. 이 경로는 Windows node_modules를 Linux 컨테이너에 덮어 씌우지 않는다. 기존 GUI 컨테이너와 `lyricscloud-local`은 별개다.

직접 Node로 실행할 때 Next rewrite 기본 목적지는 `127.0.0.1:3001`, Compose 개발은 `collaboration:3001`이다. 웹 운영 이미지는 build 시 Docker 서비스 주소를 고정한다. 다른 내부 topology를 쓰면 build 설정을 맞추거나 Caddy에서 `/collaboration`을 분리 전달한다. 공개 IP나 개발자의 주소를 코드에 넣을 필요는 없다.

## GitHub와 worktree 순서

확인 시점에 main은 초기 기획 commit이며 선택한 Phase 3보다 61 commit 뒤였다. 개발은 앞 Phase를 이어받는 `phase/<version>-p<phase>-...` 브랜치 연쇄로 누적되어 있었다. 저장소에는 별도 worktree 운영 규칙이 없었고, 이 PC는 이번에 받은 checkout 하나다. 원 개발자의 로컬 worktree 배치까지 확인한 것은 아니다. 이번에는 새 checkout에서 수정 브랜치만 분리했다.

현재 GitHub 관측은 다음과 같다. 이는 수정본의 원격 검증 결과가 아니다.

- [기준 SHA의 CI](https://github.com/parking-place/LyricsCloud/actions/runs/33953973020)는 verify와 네 image publish가 성공했다. 당시 CI에는 생산 이미지 실행 검사가 없었다.
- [열린 PR #1](https://github.com/parking-place/LyricsCloud/pull/1)은 0.3.0 P1에서 0.2.0 P5로 향한다. 모든 Phase가 main PR로 병합된 이력은 아니다.
- 조회한 21개 branch는 protected=false, repository ruleset은 0개였다. 권한 설정은 바꾸지 않았다.
- `phase/**` push는 성공한 CI 뒤 Docker Hub의 버전/전체 SHA/Dev/Dev-latest tag 발행을 유발한다. 작업 브랜치 push도 외부 image 발행 영향을 가진다.

진행 순서는 **이 Phase 3 보완 검토 → 승인된 Phase branch 원격 반영 → CI·같은 SHA image·개발 서버 smoke → Phase 4 revision → Phase 5 통합 검증**이다. Phase 4는 변경된 내용의 5분/중요 작업 snapshot, 180일·200개 보존, 비교와 복원 전 현재본 보존이 대상이다. main merge·릴리스·운영 서버 반영은 별도 결정이다.

다음 병렬 작업에 worktree가 필요하면 현재 기준 ref와 dirty 상태를 먼저 확인하고, 각 작업의 port·Compose project·volume·환경 파일을 분리한다. 이 저장소의 전체 builder-cache prune 명령을 다른 프로젝트까지 공유하는 PC에 그대로 적용하지 않는다.
