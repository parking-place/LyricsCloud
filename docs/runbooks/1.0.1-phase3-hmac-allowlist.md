# 1.0.1 P3 HMAC 허용 목록 운영 인수

## 적용 계약

`.test_users`의 최종 형식은 환경, `auth-bootstrap` purpose, `nfkc-trim-lower-v1`, `kid`에 결합된 HMAC-SHA-256 JSONL이다. HMAC은 익명화가 아니다. 레코드와 keyring을 함께 얻거나 후보 주소를 아는 공격자는 대입을 시도할 수 있으므로 두 파일을 분리하고 Git, image, 로그에 넣지 않는다.

정규화는 기존과 같은 NFKC, 앞뒤 공백 제거, 소문자화만 수행한다. Gmail의 점과 `+` 별칭은 제거하지 않으며 서로 다른 주소로 유지한다. 개발과 릴리스는 같은 메일 집합을 쓰더라도 환경별 digest와 keyring을 따로 만든다.

## 최초 이행과 rollback

1. `.test_users`, keyring, backup key를 mode `600`으로 준비한다.
2. `scripts/provision-auth-allowlist-keys.mjs`로 환경별 최초 `kid`를 만든다.
3. `scripts/migrate-test-users-hmac.mjs --dry-run`의 입력 수와 중복 제거 수만 확인한다. 주소는 출력되지 않는다.
4. `--apply`는 평문을 AES-256-GCM backup으로 먼저 새 파일에 기록하고 fsync한 뒤 `.test_users`를 원자 교체한다. 기존 backup은 덮어쓰지 않는다.
5. runtime allowlist와 keyring을 UID `65532`, mode `400`으로 각각 stage하고 web을 재생성한다.
6. 기존 허용 계정 로그인, 미허용 계정 거부, live/ready를 확인한다.

```bash
install -d -m 0700 .private/runtime
sudo install -o 65532 -g 65532 -m 0400 .test_users .private/runtime/auth_allowed_emails
sudo install -o 65532 -g 65532 -m 0400 \
  .private/keys/auth_allowlist_hmac_keyring .private/runtime/auth_allowlist_hmac_keyring
```

복원은 쓰기 가능한 격리 경로에서 먼저 검증한다. 실제 `.test_users` 복원은 평문을 다시 만드는 작업이므로 장애 rollback 때만 명시적 확인 문자열과 함께 수행한다.

```bash
node scripts/migrate-test-users-hmac.mjs --restore \
  --backup-input .private/backups/test-users-pre-hmac.enc \
  --backup-key .private/keys/auth_allowlist_migration_backup_key \
  --target .private/runtime/test-users-restore-check \
  --environment development --confirm restore-plaintext
```

복원본의 SHA-256이 backup metadata와 일치하는지만 확인하고 내용을 출력하지 않는다. 임시 평문은 검증 직후 제거한다. 암호화 backup은 기존 계정 로그인과 P4 DB grant 이행이 검증되고 운영자가 정한 rollback 기간이 끝나기 전에는 삭제하지 않는다.

## key rotation

old/new 검증 기간은 새 active key를 추가하고 직전 active key에 미래 UTC `notAfter`를 지정해 연다.

```bash
node scripts/provision-auth-allowlist-keys.mjs --rotate \
  --kid development-2026-10 \
  --old-not-after 2026-10-08T00:00:00.000Z
```

기존 레코드는 원래 `kid`와 digest를 그대로 유지하며 old digest를 새 key로 다시 HMAC한 값을 이메일 digest로 취급하지 않는다. 새 key로 bootstrap 레코드를 다시 만들어야 할 때는 인증된 평문 identity source를 복원·검증한 뒤 새 backup 경로로 이행한다. revoked 레코드를 임의로 active로 바꾸거나 삭제하지 않는다. keyring은 최대 8개이며 active key에는 `notAfter`를 두지 않는다.

새 runtime keyring을 stage하고 web을 재생성한 뒤 old/new 레코드 로그인과 환경 불일치 거부를 검증한다. old deadline 뒤 유효 레코드가 하나도 없으면 readiness가 실패하도록 구성 검증이 닫힌다. P4 grant 이행 전에는 마지막으로 기존 bootstrap 계정이 의존하는 old key를 제거하지 않는다.

## 실패 시 중단 조건

- keyring 누락·권한 오류, active key 만료 설정, 알 수 없는 `kid`
- 환경·purpose·정규화 버전 불일치, 중복 레코드, 잘못된 digest
- 원자 교체 또는 디렉터리 fsync 실패
- 암호화 backup 인증 실패 또는 source hash 불일치
- 기존 허용 계정 로그인 실패, 미허용·다른 환경 계정 허용

실패하면 기존 실행 컨테이너와 DB volume을 유지한다. 평문이나 key를 로그로 조사하지 않고 오류 코드, 파일 권한, 환경 이름, `kid`만 확인한다.
