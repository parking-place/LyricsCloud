## 기준 환경과 데이터 보호

로컬 계측 host는 Linux x86_64 8 CPU/16 GiB, Docker 26.1.5 overlay2이고 test runtime container에는 별도 hard limit가 없다. 출시 기준 자체 운영 개발 서버는 Linux x86_64 4 vCPU/8 GiB, Docker 29.8.0 overlayfs, PostgreSQL 18.6이며 `max_connections=100`, `shared_buffers=128MB`, `work_mem=4MB`, `effective_cache_size=4GB`다. 최종 commit 배포 후 같은 SHA의 disposable `postgres_test`에서 기준을 다시 실행한다.

본문은 `합성` prefix와 순번으로만 생성한다. 결과에는 본문을 넣지 않고 건수, byte, SHA-256 fingerprint만 남겼다. 실제 사용자 창작물·세션·OAuth 값은 사용하지 않았다.

각 실행 내부에서 warm-up 후 7 sample×3 round를 수행했고, 아래 값은 세 실행 중 가장 느린 p95다. 오류율은 모든 지표에서 0%였다.

## 검색 계획

1글자는 높은 일치율 때문에 `Seq Scan`, 2글자는 trigram 선택도 한계와 fixture 분포 때문에 `Seq Scan`이 선택됐다. 일반 희소어도 1,500개 가사·약 6 MB projection에서는 default planner가 약 4.9 ms의 `Seq Scan`을 더 싸게 선택했다. index-eligible probe에서는 `Bitmap Index Scan`과 `lyrics_search_body_trgm_idx`를 사용해 0.262 ms에 6행을 찾았다. 짧은 검색과 일반 검색 모두 별도 p95 budget을 만족한다.

## 저장·동시성·소크

자동 저장 probe는 1,000 change event를 한 최신 draft로 합친 뒤 합성 오류 1회를 표시하고 사용자 재시도로 같은 draft를 저장했다. 같은 row version의 동시 관계형 write 2개는 1개만 commit되고 다른 1개가 명시적 conflict가 됐으며 무음 손실은 0이었다.

24시간 가속 시험은 86,400 change event와 시간당 flush 24회를 수행했다. Node RSS 순증은 계측 해상도에서 0 MiB였고 timer·queue가 누적되지 않았다. 실제 브라우저 네트워크 지연·단절·재연결·server restart의 원문 보존과 중복 0은 `tests/e2e/lyric-sync-resilience.spec.ts`, `tests/e2e/logout-drafts.spec.ts`, `scripts/verify-production-revisions.mjs`에서 다시 실행한다.

## N+1 수정 전후

기존 worker는 선택된 account/resource/template마다 DELETE를 한 번씩 실행하고 song마다 자식 DELETE를 추가했다. 이 fixture에서는 350개 대상에 최소 350개 DELETE statement가 필요했다. 변경 후 account, song 자식, 선택 resource, template을 각각 UUID array의 set 기반 DELETE로 처리해 같은 fixture의 대상 DELETE를 2개(resource/template)로 줄였다. 실제 purge 총 시간은 위 3회 최악 284.671 ms이고 count·30일/7일·owner 격리·멱등성 계약은 기존 DB 통합 시험으로 보호한다.

## 전체 RC와 결함

RC pipeline은 clean migration 2회, upgrade/recovery migration, 정적 검사, 단위·DB 통합, production build, 성능 gate, production image/fresh DB, 전체 E2E, 5-browser 10,000줄·15화면 회귀를 한 GitHub Actions verify job에서 실패 즉시 중단한다. 재실행으로 실패를 숨기는 retry 옵션은 없다.

로컬 RC 실행은 migration 2회, check, 58 files/213 tests, production build, 성능 gate, 전체 PC/mobile E2E 223 pass·27 skip, Chromium·Firefox·WebKit desktop과 Chromium·WebKit mobile RC 10/10을 연속 통과했다. 시각 회귀가 재촬영한 기존 PNG는 제품 차이가 없어 승인된 HEAD 기준선을 유지했다.

현재 미해결 성능 P0/P1 0건이다. production build의 Yjs 중복 import 경고는 실제 메모리 증가·동기화 오류로 재현되지 않았지만 기존 P2 `RC-090-002`로 계속 추적하며, Phase 3 최종 build 로그에서 다시 판정한다.
