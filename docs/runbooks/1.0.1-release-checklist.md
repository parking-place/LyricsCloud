# 1.0.1 Private Beta 릴리스 체크리스트

이 문서는 P9에서 준비하고 P10의 최종 main SHA·CI·image digest·배포 결과로 완성한다. 값 자체가 secret인 항목은 값 대신 존재·권한·검증 결과만 기록한다.

## 후보와 승인

- [x] VERSION과 11개 package가 `1.0.1`이다.
- [x] P1~P9 구현·실제 환경 인수가 연결됐다.
- [x] 미해결 제품 P0/P1은 0건이다.
- [x] 사용자가 모든 Phase 완료 뒤 릴리스 서버 배포를 승인했다.
- [x] 사용자가 release Google OAuth와 DB 자격 증명을 개발 환경과 같은 값으로 쓰도록 지시했다.
- [x] 사용자가 외부 backup 구축을 후속으로 미루는 현재 위험 예외를 승인했다.
- [ ] P10 최종 main SHA와 병합 commit을 기록한다.
- [ ] 같은 SHA의 필수 원격 CI 성공을 기록한다.

## 코드·DB·실행 환경

- [x] `config/environment-schema.1.0.1.json`의 web·collaboration·worker·migrate·admin 계약을 검사했다.
- [x] release는 `APP_CHANNEL=release`, `APP_PHASE` 미설정이다.
- [x] migration `0900_beta_access.sql`→`0901_beta_signup.sql` fresh/reapply와 PostgreSQL 경쟁을 통과했다.
- [x] application-first rollback은 최신 forward-compatible schema를 유지한다.
- [x] 네 app image는 nonroot UID 65532·read-only root·healthcheck를 사용한다.
- [ ] 최종 web·collaboration·worker·migrate digest를 manifest에 기록하고 digest로만 배포한다.
- [ ] migration 전후 schema와 기존 사용자 자료 canary를 확인한다.

## 인증·키·가입 중단

- [x] Google redirect는 release의 정확한 HTTPS callback만 허용한다.
- [x] allowlist HMAC keyring, beta index key, beta AEAD key는 환경별 목적과 파일 경계가 분리된다.
- [x] web에는 allowlist keyring과 beta index key만, admin에는 beta index/AEAD key만 제공한다.
- [x] runtime secret은 소유자 전용 mode 400, 관리/원본 key는 mode 600 이하로 확인했다.
- [x] 기존 bootstrap 사용자와 code 가입 모두 blocked/revoked principal을 우회하지 못한다.
- [x] kill switch는 관리자 `refresh --confirm-environment release`로 unused code와 pending intent를 폐기하고, 필요 시 신규 code 발급을 중단한다. 기존 grant·사용자 자료는 자동 삭제하지 않는다.
- [ ] 배포 후 허용된 기존 계정 session과 실제 Google 신규 가입을 각 1회 확인한다.

## 역할과 중단 조건

| 역할 | 현재 책임 |
|---|---|
| 릴리스 실행 | Codex가 승인된 자동 절차와 정확한 SHA/digest만 사용 |
| 운영 판단 | 저장소/서버 소유자가 공개·중단·rollback 결정 |
| 최초 지원 | version·SHA·익명 error code·requestId만 수집 |
| 보안/데이터 | 인증 우회·교차 owner·무음 손실·secret 노출을 즉시 P0/P1 재분류 |
| 복구 | 호환 app rollback 또는 새 빈 DB 격리 restore, 기존 DB/volume 덮어쓰기 금지 |

아래 중 하나라도 발생하면 moving alias와 릴리스 배포를 중단한다.

- 전체 CI 실패 또는 최종 SHA 불일치
- migration transaction 실패, schema 불일치, 기존 자료 canary 불일치
- 로그인/가입 우회, 교차 사용자 노출, 저장 후 재진입 손실
- 네 서비스 중 하나의 ready 실패, 합성 편집·동기화 실패
- image secret canary 또는 수정 가능한 HIGH/CRITICAL 취약점 발견

배포 후 실패하면 신규 app 세 서비스를 함께 중지하고 직전 승인 digest로 application rollback한다. DB schema는 유지하며 파괴적 down migration을 금지한다. schema/데이터 무결성 문제가 있으면 쓰기를 중단하고 최신 유효 archive를 새 빈 DB에 복원해 검증한 뒤 연결 대상을 바꾼다.
