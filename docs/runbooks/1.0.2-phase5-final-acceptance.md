P5 후보는 `8d55ddc2a5b2383bc7388a248bb7d66f13a5bd0b`, GitHub Actions는 [run `34436900678`](https://github.com/parking-place/LyricsCloud/actions/runs/34436900678)이다. 1.0.2의 DB migration 추가는 없으며 최신 schema는 `0901_beta_signup.sql`이다.

주요 변경 파일은 다음 경계다.

- 운영 인수: 현재 문서, CI runtime metadata, release/environment validator

## P5 로컬·원격 검증

후보 commit 전 다음을 실행한다.

```bash
pnpm check
pnpm build
pnpm test:release:1001
pnpm test:release:1002
pnpm test:release:1004
pnpm test:release:1005
pnpm test:environment:101
```

최종 push는 `[skip ci]` 없이 수행했다. run `34436900678`의 verify job에서 migration, unit/integration, production build, production image, backup/restore, vulnerability/secret, 전체 Playwright와 release browser matrix가 모두 성공했다. 이어 web·collaboration·migrate·worker publish job 네 개도 성공했고 개발 계열만 발행했으며 정식 별칭은 이동하지 않았다.

## 개발 환경 인수

CI가 통과한 정확한 후보 SHA를 개발 서버에 배포한다. 기존 PostgreSQL volume과 비공개 secret을 보존하고 migrate를 먼저 통과시킨다. public HTTPS에서 live·ready·auth·정적 asset을 확인하며 ready는 다음을 반환해야 한다.

```text
version=1.0.2
build.id=<정확한 후보 SHA>
channel=dev
phase=p5
database.schemaVersion=0901_beta_signup.sql
```

web·collaboration·worker·postgres가 모두 healthy가 아니거나 공개 metadata가 다르면 완료하지 않는다. 검증 성공 뒤 서버 Docker build cache를 정리하되 volume은 정리하지 않는다.

후보 SHA를 개발 서버에 배포한 결과 checkout과 `.env` `BUILD_ID`, 공개 live/ready build ID가 모두 정확히 일치했다. 두 health endpoint는 `version=1.0.2`, `channel=dev`, `phase=p5`를 반환했고 ready schema는 `0901_beta_signup.sql`이었다. 네 상시 서비스는 healthy였으며 `/auth` 200, production JavaScript asset 200, CSP·private no-store·nosniff를 확인했다. 정리에서 약 1.59 GB build cache를 회수했고 PostgreSQL volume과 실행 중 컨테이너를 보존했다.

## P0/P1와 잔여 위험

P5까지 실제 범위의 새 P0/P1, 원문 유실, 인증 우회, 교차 사용자 노출, 무음 저장 성공은 0건이다. 외부 backup 미구축 `OPS-100-001`과 상세 기기 정보가 없는 과거 iOS/Android 증거 `RC-091-002`는 그대로 남는다.

## 중단·rollback

- CI 실패: 실패 SHA를 배포하지 않고 원인을 수정해 새 후보로 다시 검증한다.
- 개발 migration/health 실패: volume을 삭제하지 않고 직전 P4 SHA로 application-first rollback한다.
- 저장·가입·권한 P0/P1: 공개 개발 배포를 중단하고 합성 증거만 보존해 비공개 보안/장애 절차로 전환한다.
- release 승인 부재: 후보 인수까지만 완료하고 main·tag·정식 image·릴리스 서버는 그대로 둔다.
