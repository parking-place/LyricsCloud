# 1.0.14 Phase 4 — 실제 입력·성능·개인 기능 통합 후보

## 검증 경계

- 자동 환경은 Linux x86_64의 Chromium desktop/mobile viewport이며 실제 Windows 한글 IME·Android/iOS 키보드나 물리 저사양 기기가 아니다.
- Playwright가 platform IME를 직접 구동할 수 없으므로, 실제 편집기의 composition 경계 사이에 문서 변경을 넣어 지연 저장 경로를 합성한다. 폰트 응답이 느린 동안 편집기 DOM·focus·selection이 유지되고, 응답 완료 뒤 commit·서버 저장·재진입 원문이 같은지 확인한다.
- 2,000줄 문서, 4배 CPU throttle, 8회 font family 교체로 렌더 proxy와 GC 뒤 JS heap 증가를 측정한다. 이 수치는 실제 기기 frame·브라우저 native font memory를 대신하지 않는다.
- 기존 전체 E2E의 mode/copy·목록 정렬·Suno 수동 링크·PWA offline/reconnect를 재사용하고, P4 신규 검사는 폰트 로딩과의 새 상호작용만 추가한다. 1.0.13 사전은 provider no-go라 함께 사용할 구현이 없다.

## 예산과 실패 계약

- cold 선택: font 요청 1건, 4,700,000 bytes 이하.
- 이미 캐시된 warm/offline font: 서비스워커 회귀에서 추가 네트워크 0건.
- P2 대비 전체 정적 JS chunk gzip 증분: 20KB 이하.
- 4배 CPU throttle font switch 최대 2,500ms 미만, 8회 교체 후 GC된 JS heap 증가 32MiB 미만. 이는 회귀 차단용 합성 상한이며 물리 기기 지원 주장이 아니다.
- 느린/차단 font 요청에서도 system sans fallback으로 원문이 보이고 입력·서버 저장·새로고침을 막지 않는다.

## 자동 검증 결과

- desktop/mobile Chromium 4건 PASS: 각 cold font 요청 1건, `4,644,748` bytes.
- 4배 CPU throttle의 8회 전환 최대값: desktop `51ms`, mobile `48ms`.
- GC 뒤 JS heap 증분: desktop `318,884` bytes, mobile `327,332` bytes.
- P2→P3 정적 JS chunk gzip: `570,156`→`572,363` bytes, 증분 `2,207` bytes.
- PWA desktop 2건 PASS: immutable font를 cache한 뒤 offline fetch가 성공하고, private API/페이지는 cache하지 않았다.
- font 요청 차단에서도 fallback 원문 표시, 추가 입력, 서버 저장, reload 후 동일 본문을 desktop/mobile에서 확인했다.

## 미실행과 release 판단

실제 Windows/Android/iOS의 1.0.14 font switch·늦은 로딩·장문 입력은 실행 환경이 없어 미실행이다. 이전 1.0.1의 Windows Chrome/Edge 및 iOS/Android 입력 PASS는 기존 저장 baseline으로만 재사용하며 신규 폰트 물리 증거로 확대하지 않는다. 자동/공개 회귀가 통과하더라도 이 물리 위험은 P5 release note에 남긴다.
