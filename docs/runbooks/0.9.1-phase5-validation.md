## 현재 로컬 증거

- backup image: PostgreSQL 18 client + digest 고정 Go 1.26.8로 빌드한 공식 age 1.3.2, non-root `postgres`, read-only rootfs 실행
- 예정 실행 2회와 30일 retention: PASS
- 정상/24시간 초과 RPO 판정: PASS
- read-only storage, 용량 부족, ciphertext 손상, 잘못된 identity: 모두 명확한 실패와 기존 정상 archive 보존 PASS
- 독립 restore: schema `0802_lifecycle.sql`, 4개 검색 index, forced RLS 위반 0, CRDT orphan 0, 복원 DB 대상 web·collaboration·인증 목록 product smoke PASS
- owner 격리·검색·CRDT snapshot/projection fingerprint: PASS
- encrypted archive의 가사·라임·프롬프트·revision 합성 평문 canary: 0건
- web·collaboration·worker·migrate·backup image의 수정 가능한 High/Critical 취약점: 0건, layer secret canary: 0건
- restore 측정값: 반복 실행 1.3~1.6초(300초 budget 이내)
- 이전 RC→현행 upgrade: 1.628초, migration fault rollback PASS
- 신규 image health fault→이전 RC application rollback: 2.556초(180초 budget 이내), data canary 보존·roll-forward PASS

첫 원격 실행은 기존 성능 gate의 export RSS가 allocator 최초 확장을 포함해 실패했고, 재실행에서는 기존 crash-recovery test의 임의 포트가 충돌했다. 세 번째 실행에서 export RSS가 다시 흔들려 예산은 유지한 채 OPS-0003의 공통 원칙대로 export도 warm-up 후 측정하도록 수정했다. 이 변경 뒤 전체 CI를 새 SHA로 다시 검증한다.
새 SHA에서 성능·단위 테스트는 통과했고 Phase 5 backup harness가 non-root GitHub runner에서 image UID로 `chown`하려다 중단됐다. 일반 runner는 자기 non-root UID를 유지하고 root 개발 환경에서만 image UID로 맞추도록 수정해 다시 검증한다.

실제 사용자 자료와 운영 비밀 값은 fixture·출력·Git에 사용하지 않았다. 최종 원격 run과 개발 배포 증거는 완료 commit 검증 후 추가한다.
