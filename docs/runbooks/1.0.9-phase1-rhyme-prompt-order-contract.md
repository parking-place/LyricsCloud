# 1.0.9 P1 라임·프롬프트 사용자정렬 계약 인수

- 승인: 2026-09-11 사용자 1.0.14까지 전체 Phase와 버전별 정식 릴리스 실행 지시
- 출발점: 1.0.8 main/tag source `5388bbfae54762288aea9bc4d83e81535faa385e`
- 현재 Phase: 설계-only. 아래 입력은 P2~P4의 실제 DB/API/browser와 동일 SHA 개발 인수 전까지 PASS가 아니다.

## 저장·정렬 계약

1.0.9는 1.0.8의 `library_order_states`, `library_order_items`, `library_order_move_requests`를 그대로 사용한다. 세 테이블은 이미 `song`, `rhyme_note`, `prompt`를 허용하고 기존 세 자료 유형을 owner+type+pin group별 sparse rank로 backfill했으므로 새 schema를 만들지 않는다. P2는 미소비였던 `rhyme_note`와 `prompt`의 조회·이동·추가·복제·핀 변경 경로만 활성화한다. 곡, 라임, 프롬프트의 state/version/rank/request namespace는 서로 독립이다.

라임·프롬프트의 `manual` 정렬은 핀 그룹, 해당 owner+type의 rank, 안정 ID 순이다. 다른 정렬과 기존 `pin_order`는 바꾸지 않는다. 새 자료와 복제는 현재 핀 그룹 끝에 붙고 실제 순서 변경만 type별 version을 1 올린다. soft delete는 rank를 보존하고 restore는 같은 위치를 재사용하며 hard purge만 순서 행을 cascade 삭제한다. 핀 변경은 기존 pin metadata와 함께 manual item을 새 그룹 끝으로 옮기되 다른 자료 유형이나 전역 즐겨찾기 핀 순서를 수정하지 않는다.

프롬프트 카드 순서는 `resources`의 prompt 자료 순서다. `prompt_tokens.ordinal`, occurrence, display/normalized value, tag/sentence 원문, 최종 복사 payload와 최근 사용 기록은 이동 명령의 읽기·쓰기 대상이 아니다. 라임 이동도 본문·태그·곡 연결·복사 payload를 수정하지 않는다. 미래 공유 자료가 추가돼도 개인 order state는 owner의 개인 projection이고 공유 원본 metadata를 갱신하는 권한으로 확장하지 않는다.

## API·동시성 계약

P2는 `POST /api/rhymes/order/moves`와 `POST /api/prompts/order/moves`를 추가하며 body는 곡과 같은 `{requestId,itemId,beforeId,afterId,expectedVersion}` 다섯 필드만 받는다. owner, resource type, rank, 전체 ID 배열, 검색·필터 값과 알 수 없는 필드는 받지 않는다. route가 고정한 type과 인증 owner를 서버 transaction 경계에서 사용한다.

필터 목록은 이동 뒤 보이는 이전/다음 항목만 after/before anchor로 보낸다. 서버는 owner+type advisory lock, expected version, active 대상/anchor, 같은 pin group, anchor 순서를 검사한다. 다른 owner·삭제된 ID는 존재 여부를 숨긴 404, pin group 교차는 409, stale version과 request ID 재사용 불일치는 409다. 동일 request ID·동일 payload는 같은 결과를 replay하고 실제 이동이 없는 요청은 version을 올리지 않는다.

GET `/api/rhymes?sort=manual`과 `/api/prompts?sort=manual`은 `orderVersion`과 manual-order capability를 반환한다. manual cursor에는 query signature, pin group, rank, stable ID, 해당 type order version이 포함된다. 이동 뒤 이전 cursor는 409로 중단하고 UI는 첫 페이지를 다시 읽는다. 검색·favorite·연결 곡·태그·최근 사용 필터로 숨긴 자료나 아직 불러오지 않은 페이지를 전체 배열 저장으로 삭제하거나 재순위하지 않는다.

## 실패 우선 입력표

| 입력 | 먼저 확인할 실패 | P2~P4 기대 |
|---|---|---|
| 프롬프트 카드 이동 뒤 전체 복사 | card 순서가 token ordinal/payload를 변경 | 카드 순서만 변경, token occurrence와 exact copy 불변 |
| 라임 카드 길게 누르기와 handle drag | copy와 drag가 함께 실행 | handle만 drag 시작, card long press copy와 단일 실행 |
| favorite/곡/태그 필터에서 이동 | 숨은 자료 삭제·전체 배열 저장 | visible anchor만 전송, 숨은 상대 순서 보존 |
| soft delete 뒤 restore | 중복 order item·끝 append | 기존 item 한 행과 같은 계약 위치 복원 |
| 곡→라임→프롬프트 연속 이동 | 한 version/rank namespace 혼합 | 세 type version·rank·전역 pin metadata 독립 |
| 같은 type 두 탭·동일 version | last-write-wins·중복 version | 한 성공·한 409, 최신 첫 페이지 수렴 |
| 이동 중 network abort/500 | 낙관 순서 고착·원문 편집 차단 | 원래 배열 복원·동일 request 재시도, 편집 원문 보존 |
| 다른 owner item/anchor | 존재·제목·순서 노출 | indistinguishable 404, 양쪽 state 불변 |
| midpoint 소진 | 전체 owner/type 재작성 | 현재 owner+type+pin group만 bounded rebalance |

구버전 client는 새 route와 `manual` sort를 사용하지 않으므로 기존 목록 정렬을 유지한다. application-first rollback은 라임·프롬프트의 이동 UI/API와 manual 선택을 숨기고 기존 기본 정렬로 돌아간다. 1002 테이블은 이미 1.0.8 운영 호환 schema이므로 삭제하거나 down migration하지 않는다. 실제 물리 기기를 수행하지 않으면 browser 자동화를 실기기 PASS로 기록하지 않는다.
