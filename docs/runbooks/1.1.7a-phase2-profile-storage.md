# 1.1.7a P2 — 프로필 저장과 비공개 사진 경계

상태: P2 구현 후보. P2 전체 CI·같은 SHA 개발 서버와 공개 smoke가 완료되기 전에는 수용 완료가 아니다. 기준은 `v1.1.7`에서 분기한 `release/1.1.7a`의 P1 merge `86fa946`이며 main의 1.1.8 Windows 코드는 포함하지 않는다.

## 데이터·이행

`1151_profile_customization.sql`은 기존 `user_profiles.display_name/avatar_url/created_at/updated_at`, `auth_identities`, 자료와 볼륨을 지우지 않는다. 모든 기존 profile의 효과값은 그대로 두고 source를 `legacy_unclassified`로 표시한다. 당시 최신 Google identity는 별도 `provider_display_name/provider_avatar_url`에 복사하지만 효과값의 출처를 추정하지 않는다. 후속 Google 로그인과 beta 가입 재시도는 provider 기본값만 갱신하며, source가 `provider`인 필드만 새 기본값을 표시한다. `override`와 `legacy_unclassified` 효과값은 그대로 둔다. 사용자가 명시적으로 `null` 복귀하면 source는 `provider`가 되고 최신 Google 값, 이름이 없다면 `사용자` fallback을 표시한다.

`profile_avatar_photos`는 서버 생성 UUID, owner FK, 200 KiB 이하 WebP `bytea`, SHA-256과 force RLS를 가진다. profile의 `(owner_id,avatar_photo_id)` 복합 FK는 타인 사진 참조를 막는다. 사진 교체/복귀는 owner profile row lock, 새 사진 insert·참조 변경·이전 사진 delete를 한 transaction으로 수행한다. 검증 실패·충돌·서버 중단이면 transaction 전체 rollback으로 현재 사진이 유지된다. 사진의 public URL은 만들지 않고 현재 owner의 식별자 없는 `/api/profile/avatar`만 cookie 인증과 현재 참조 확인 후 읽는다. 교체 시 같은 URL은 항상 현재 사진만 반환하고 명시 복귀 뒤 404다. `Cache-Control: no-store`, `nosniff`, WebP만 제공하며 개인 사진 ID는 URL/프록시 로그에 남지 않는다. export의 `profileAvatarPhotos`에 owner 사진의 base64 WebP를 포함하고, 회원 완전 삭제는 `app_users` cascade로 사진까지 지운다.

## P3가 소비할 HTTP 계약

- `GET /api/profile`: active cookie session. `profile`에 효과 `displayName`, 효과 `avatarUrl`, `displayNameSource`, `avatarSource`, `rowVersion`를 반환한다. 사진 URL은 같은 owner cookie로만 읽을 수 있다.
- `PATCH /api/profile`: 정확한 same-origin, JSON `{ expectedRowVersion, displayName?: string | null, avatar?: null }`. 공백 trim/빈 문자열·120 Unicode 문자 초과는 400. 생략은 다른 필드 유지, `null`은 provider 기본값 복귀. 원격 `avatarUrl`, client owner/photo id는 입력하지 않는다. stale 두 탭은 409 `VERSION_CONFLICT`와 최신 서버 `error.details.profile`; 사용자의 입력을 응답에서 지우지 않는다. 같은 version의 중복 요청은 stale conflict로 안전하게 멈춘다.
- `PATCH /api/profile/avatar`: 정확한 same-origin, multipart `expectedRowVersion`과 로컬 `avatar` File. 이 route 하나만 일반 API 1 MiB body 상한 대신 2 MiB 파일+50 KiB multipart 상한이며 초과는 proxy 413이다. PNG/JPEG/WebP 실제 signature, 파일 2 MiB 이하, 단일 프레임, 16 MP 이하, Sharp 실제 decode/auto-rotate/256×256 cover/WebP 재인코드, 200 KiB 출력 상한. SVG/GIF/URL/손상/위장/과대는 400이고 원본 파일명·EXIF는 저장하지 않는다. 성공하면 위 `profile`을 반환하고 닉네임은 유지된다. 취소는 업로드를 보내지 않는다.
- `GET /api/profile/avatar`: 현재 owner의 현재 사진만 200 `image/webp`; 다른 owner/익명은 404/401. 식별자 query는 404. 공유 페이지, 공개 token, 로그·분석에 사진 ID/bytes를 넣지 않는다.

## 롤백·복구

배포 실패 시 먼저 직전 `v1.1.7`의 검증된 image/digest로 앱을 되돌린다. `rollback/1151_profile_customization.sql`은 의도적으로 추가 schema/사진을 삭제하지 않으며 재배포 때 migration 재실행은 멱등이다. 이전 앱은 효과 `display_name/avatar_url`을 읽을 수 있다. 단, 새 DB 사진 override는 이전 앱의 원격 avatar URL로 표시되지 않으므로 앱 롤백 중 사진은 fallback/미표시일 수 있고 DB 사진 자료는 보존된다. schema의 destructive reversal은 신규 쓰기 중지·해당 owner 자료/사진 백업·별도 명시 승인이 있어야 한다. 기존 Google issuer/subject/email과 sharing ID는 프로필 PATCH 경로에서 수정하지 않는다.

## 검증

`pnpm test:migration:1151`은 채워진 1140 데이터→1151, migration 반복, legacy/provider 분리, 사진 RLS, 비파괴 app-first rollback/recovery를 disposable DB에서 검사한다. `profile-customization.integration.test.ts`, `beta-signup.integration.test.ts`, `profile-input.test.ts`, `profile-avatar.test.ts`, `profile-117a-api.spec.ts`는 두 owner, CAS, 재로그인/가입, 실제 재인코드/거부, HTTP owner·cache·사진 제거를 검사한다. 공유 이름 projection은 성공 후 현재 `user_profiles.display_name`을 읽고 이름 off 정책과 과거 감사 actor 기록은 그대로 유지한다. 실제 CI·개발 서버 공개 결과는 Phase 문서/STATUS에 별도 기록한다.
