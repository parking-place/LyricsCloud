# LyricsCloud 1.1.7a 전용 릴리스 실행·되돌리기

상태: P5 최종 후보·운영 배포 대기. 사용자 2026-09-16 승인으로 이번 한 번 `v1.1.7` source에서 분기한 `release/1.1.7a` PR/CI/tag를 사용한다. `main`의 미완료 1.1.8 Windows와 기존 `v1.1.7` tag/image/DB volume은 이동하거나 삭제하지 않는다.

## 진입 게이트

P1~P5 완료, P5 최종 Phase 브랜치의 정확한 SHA 전체 CI·네 signed dev image, 같은 SHA 개발 서버 `1.1.7a/dev/p5`·1151 migration·네 health·공개 저장/재진입/권한/홈 smoke를 먼저 확인한다. 기록에 실제 OS/기기·IME/AT 미실행과 `OPS-100-001` 외부 backup/24시간 RPO 미구축 예외를 남긴다. 제품 P0/P1·원문 유실·인증 우회·타 owner 사진 노출이 있으면 출시하지 않는다. 문서-only `[skip ci]`를 최종 CI PASS로 대체하지 않는다.

## 승인된 전용 release 경로

P5 PR을 `release/1.1.7a`에 병합해 merge tree와 reviewed P5 후보 tree를 대조하고, **병합 SHA 자체**에서 필수 CI와 동일 SHA 개발 인수를 확인한다. 다른 버전의 main을 병합하지 않는다. SHA에 annotated `v1.1.7a`를 한 번만 만들고 tag를 이동하지 않는다. 정확한 tag의 수동 workflow에서 `publish=true`, `release=true`를 실행해 web/collaboration/worker/migrate 각각 immutable `1.1.7a`·full SHA·`Release`·`latest`·`Release-latest`가 **서비스별 동일 exact digest**인지 확인한다. signature·provenance·SBOM와 `config/release-manifest.1.1.7a.json`의 실제 checksum·schema를 대조한다. moving alias 부분 실패면 운영 전환을 멈추고 이미지별 상태를 기록한다.

릴리스 서버의 현재 checkout·실행 SHA/digest·DB schema·네 health·allowlist/beta CLI와 `.env`/secret/volumes를 **읽기 전용**으로 확인한 뒤, 승인한 migrate digest를 한 번 먼저 실행한다. schema `1151_profile_customization.sql`과 기존 자료가 유지된 것을 확인하고 web/collaboration/worker를 승인 exact digest로 전환한다. 개발 서버 비밀값을 릴리스 서버로 복사하거나 운영 DB/볼륨을 개발과 혼합하지 않는다. 기존 운영 Google Client/DB 비밀번호를 개발과 같은 값으로 유지하겠다는 사용자의 지시는 비밀값 출력·커밋 허가가 아니다.

공개 HTTPS에서 live/ready `1.1.7a/release`·전체 build SHA·1151 schema·네 health와 `/auth` 200, 익명 사진 401을 검사한다. 실제 사용자 계정/코드 대신 합성 owner 두 명으로 닉네임/사진 저장→재진입·재시작 지속, 타 owner 사진 차단, Google 제공값/override, PC/mobile 양 theme 우측 홈 icon/dirty guard, 위장 파일 거부/이전 사진 유지, 공개/선택 공유의 이름 노출 설정·사진 비공개, export/탈퇴 경계를 확인한다. 합성 사용자·세션·사진은 자료 범위를 정확히 지정해 삭제 후 0건을 확인한다. 공개 지원/릴리스 노트와 비공개 운영 inventory에는 SHA·digest·승인/검증/rollback·미실행을 기록하되 이메일/사진/세션/비밀값은 남기지 않는다.

## application-first rollback

health·저장·권한 smoke가 실패하면 새 쓰기를 멈추고 검증된 이전 `v1.1.7`의 **서비스별 exact digest**로 앱 세 서비스를 되돌린다. 1151 schema·사진 자료·기존 PostgreSQL volume은 삭제하지 않고 재검증한다. 이전 앱은 신규 DB 사진을 fallback/미표시할 수 있다. destructive DB down migration/복원은 외부 backup·새 빈 격리 DB 검증과 별도 명시 승인 없이 실행하지 않는다. 운영 host-loss 복구 지점은 현재 예외로 보장되지 않는다.
