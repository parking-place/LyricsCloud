# 1.0.12 정식 릴리스 실행

## 승인과 source

사용자는 1.0.12 P1~P5 완료 뒤 정식 main 병합·image·릴리스 서버 배포를 승인했다. Phase PR을 순서대로 병합하고 최종 main 전체 CI와 동일 SHA 개발 인수를 통과한 commit에 annotated `v1.0.12` tag를 만든다. tag는 이동하거나 재사용하지 않는다.

## image와 배포 순서

1. annotated tag의 workflow를 `publish=true`, `release=true`로 실행한다.
2. web·collaboration·worker·migrate의 서명·provenance·SBOM과 exact digest를 확인한다.
3. 네 digest가 같은 source SHA인지 확인한 뒤에만 `1.0.12`, `Release`, `latest`, `Release-latest` 별칭을 인정한다.
4. 릴리스 서버는 moving tag가 아니라 exact digest로 migrate를 먼저 한 번 실행하고 collaboration·worker·web 순서로 갱신한다.
5. live/ready의 version·build SHA·release channel·schema, owner 격리와 개인 수직 흐름 공개 smoke를 확인한다.
6. GitHub Release에 source SHA·CI run·digest·schema·알려진 제한을 기록한다.

## 중단·복구

새 P0/P1, tag/SHA/digest 불일치, migration 실패, owner 노출, 저장 후 재진입 손실, 서비스 unhealthy면 배포를 중단한다. `1003`은 additive schema이므로 application-first rollback을 우선하고 DB 파괴적 down migration은 하지 않는다. 외부 backup은 `OPS-100-001` 사용자 승인 예외로 미구축이므로 RPO를 주장하지 않는다.
