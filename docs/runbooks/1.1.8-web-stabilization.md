# 1.1.8 P4 웹 안정화 및 PC 갱신 기록

## 범위와 기준

2026-09-22 사용자가 기존 문제 수정·추가 결함 조사·계획 진행·PC Docker 갱신을 승인했다. 제품 코드는 Astra가 작성하고 독립 분석은 여러 모델이 맡았다. 작업 브랜치는 `phase/1.1.8-p4-web-stabilization`, 기준은 `21f5863` 및 기존 개발 기능 SHA `a7d8e4538c58202f4a1e39371517906e891ae1bf`다. 기존 Windows P4 실제 기기·신뢰 서명 인수와 P5·정식 릴리스 보류는 유지한다.

## 실제 재현과 수정

- 기존 기능 SHA의 production build와 별도 PostgreSQL 18 임시 DB·합성 OIDC 계정을 PC에 구성했다. Windows build 경로 오류는 `fileURLToPath`로 바로잡고 동일 소스 화면을 확인했다.
- 실제 내장 브라우저에서 곡/가사 생성·본문 입력·다시 열기·본문 복사·닉네임 저장을 확인했다. 노트북 1265×712의 도구 버튼은 폭 약 32px·높이 약 111px로 압축돼 한글이 세로로 줄바꿈됐다.
- 수정 전 production build에서 설정 저장 ACK 경쟁, 가사별 표시 설정 ACK 경쟁, 노트북 도구 배치, 휴지통 mutation 성공 후 목록 갱신 실패 회귀가 각각 실패했다. 첫 Playwright 설정은 기존 서버를 재사용하지 못해 시작 단계에서 중단됐고, 전용 설정을 바로잡은 뒤 제품 실패를 재현했다.
- 목록의 오래된 추가 응답·곡 favorite/pin 경쟁·검색 그룹의 키보드 순서·최근 검색 삭제 복원은 실제 컴포넌트 handler와 지연 네트워크 경계를 사용해 수정했다. 서버 cursor/API·schema는 바꾸지 않는다.
- 편집 실패 복사는 제목·가사 원문·메모 또는 라임/프롬프트 입력을 포함한다. 정상 Suno용 복사는 기존 형식을 유지한다. 조합 중 입력 및 메모리의 미저장 제목을 이탈/PWA guard에 표시하며, 기존 offline flush/checkpoint 계약은 유지한다.
- 공개 guest의 온라인 쓰기 권한 회수·stale epoch 거부 때 미승인 Yjs 입력이 본문/캐시에 남는 결함을 수정했다. 마지막 서버 승인 상태로 복원하고 해당 guest가 작성한 부분만 복구 보관하며 재허용 뒤 자동 재전송하지 않는다. 실제 Yjs 단위 3건에서 수정 전 FAIL→수정 후 PASS를 확인했다.

## 로컬 통합 검증

- 첫 통합 production build와 build artifact의 합성 인증 secret 누출 검사가 PASS했다. 계정/가사 표시 설정·노트북 도구·휴지통·공개 guest의 집중 Chromium 실행은 첫 시도 **8 PASS / 3 FAIL / 1 조건부 skip**이었다.
- 실패 중 설정 회귀 1건은 `<output>`의 암시적 status와 실제 저장 알림을 혼동한 test selector였다. 실제 `.settings-message[role="status"]`의 정확한 성공 문구로 보정하고 desktop 1건을 다시 PASS했다.
- guest mobile 2건은 제품 연결 실패가 아니라 desktop/mobile을 동일 fixture server에서 연속 실행해 기존 분당 IP handshake 제한의 **429**에 도달한 것이다. 제한·assertion·timeout은 그대로 두고 CI와 같은 project 분리 방식으로 mobile 2건을 재실행해 PASS했다. 실패 시도를 PASS로 소급하지 않는다.
- 실제 내장 브라우저에서 저장된 합성 가사 66자 재열기·전체 복사 원문 일치·console error 0건을 확인했다. 노트북 도구는 읽을 수 있게 개선됐지만 모바일 하단 도구의 세로 줄바꿈과 상단 상태 알림의 설정 링크 가림을 추가 발견했으므로 최종 모바일 보정·재검증 전 전체 UI 완료를 주장하지 않는다.
- 추가 모바일 보정 뒤 production build와 반응형 집중 회귀 **1 PASS**: 960/1265/1366px 노트북, 320/390px 모바일, 양 theme·기존 b1/classic 계약에서 줄바꿈/잘림·overflow 없음, 편집 공간·동일 editor instance 유지와 설정 링크 hit target을 확인했다. 실제 내장 브라우저 320px light에서도 읽을 수 있는 하단 도구와 알림 표시 중 설정 클릭→설정 페이지 이동을 확인했다. 최종 결과는 첫 실행의 8건과 영향 실패 3건 재검증을 합쳐 **집중 11 PASS / 1 조건부 skip**이며, 그중 반응형 1건은 모바일 보정 뒤 확장된 입력으로 다시 통과했다. 실제 물리 모바일 키보드/OS IME 결과는 아니다.

## 첫 최종 CI의 실패와 집중 보정

- 후보 `cd87eb283ecaf5977a8bc9552f26bfa52f273f26` / PR [#152](https://github.com/parking-place/LyricsCloud/pull/152)의 Actions [35694180993](https://github.com/parking-place/LyricsCloud/actions/runs/35694180993)은 Windows build와 migration·단위·production image·보안 검사를 통과했지만 owner E2E **368 PASS / 35 FAIL / 49 조건부 skip**으로 종료했다. 네 개발 image 발행은 skipped이며 PC 전환은 실행하지 않았다.
- 32건은 PWA 안내에 추가한 전역 `status` 역할과 기존 기능 알림의 선택자 충돌이었다. PWA 안내는 `aria-live="polite"`·`aria-atomic="true"`로 계속 전달하고, 상시 미지원 안내는 기존의 짧은 “일반 웹 모드” 표현으로 보정했다. 관련 단위 회귀는 실패 재현 뒤 **6 PASS**다.
- 복구 복사 2건은 과거 본문만 복사하는 기대값이었다. 현재 계약의 제목·원문·메모 전체를 정확히 비교하도록 기존 시험을 갱신했다. 비어 있지 않은 여러 줄 메모와 Extend 원문을 포함하고, CodeMirror의 줄별 DOM도 실제 줄 단위로 확인한다. 임계치나 원문 기대값을 완화하지 않았다.
- 곡 순서 시험의 retry에서는 키보드 이동 ACK **2.874s**보다 앞선 **2.833s**에 다음 드래그를 시작했고 새 manual 목록이 source를 교체해 C 이동 요청이 없었다. 앞선 곡의 저장 확인과 enabled handle을 기다린 뒤 다음 드래그를 검증한다. 제품 순서 코드는 바꾸지 않았다.
- PWA 안내 배치 변화로 모바일 화면 비교도 실패했다. 공식 Playwright **1.62.1 noble** Linux image에서 기존 스냅샷 6개 사례를 확인해 **4 PASS / 2 FAIL**, 실제 홈·템플릿 모바일 결과를 시각 검토한 뒤 해당 기준 2장만 갱신했고 같은 두 사례를 **2 PASS**했다. 탐색 화면은 문구 보정만으로 통과했다. 기존 **6%** 비교 허용치는 유지했다.
- 추가 검증은 영향받은 로그인/탐색/템플릿/순서/복구의 PC·모바일 **10개 고유 사례 PASS**다. 첫 Windows 실행의 미생성 고정 visual session 및 여러 줄 CodeMirror 텍스트 비교는 격리 fixture를 추가하고 줄별 비교로 바로잡았다. Windows와 Linux 렌더링은 구분하며 Linux 기준 이미지는 Linux에서만 갱신했다. 자동으로 바뀐 과거 증거 PNG 6장은 기존 blob으로 복원하고 새 출력은 비공개 검증 폴더에 보존했다. 최종 `pnpm check`와 production build도 PASS다.
- 보정 후보의 필수 CI와 PC 갱신은 새 SHA에서 확인한다. 실패한 첫 CI를 PASS로 재분류하지 않는다.

### 두 번째 CI의 모바일 탐색 기준 보정

- 후보 `a15271003e686995579ce3ddff26c4ac29c5dcbf`의 Actions [35697819946](https://github.com/parking-place/LyricsCloud/actions/runs/35697819946)은 owner E2E **402 PASS / 1 FAIL / 49 조건부 skip**으로 종료했다. Windows build·DB·production image·보안 검사는 PASS했고 개발 image 발행과 PC 전환은 실행하지 않았다.
- 남은 실패는 모바일 즐겨찾기 빈 화면의 이전 기준에서 **21,500 pixels / 7%** 차이였다. 그 기준에는 현재의 일반 웹 모드 안내 행이 없었다. 앞선 Linux 집중 실행은 6% 허용치 안이었지만 CI에서는 이를 넘었으므로, 단순 재실행 대신 같은 안내 행의 영향을 받는 모바일 최근 작업·즐겨찾기·검색 loading/empty/error 5장을 공식 Playwright 1.62.1 noble 환경에서 다시 생성하고 각각 시각 검토했다.

## PC 복구 사본과 갱신 경계

- 기존 `lyricscloud-local`은 `1.0.0`, build `405e5351454bc3965227d5c824f9c996f6cc0233`, schema `0802_lifecycle.sql`이었다. DB volume 이름은 `lyricscloud-local_postgres_data`다.
- 외부 백업 설정이 없다는 안내 뒤 사용자는 “없을거같으면 그냥 업데이트 해줘”라고 승인했다. 로컬 `.private/backups/pre-web-stabilization-20260922/`에 DB dump와 기존 환경/허용 목록/Compose 복구 사본을 만들고 사용자 전용 Windows ACL을 적용했다. 내용을 출력하거나 Git에 넣지 않는다.
- DB dump 159,140 bytes, SHA-256 `e2bad71585707720d3be18dc3461d5585032f3d93c9de726e49bb41ee8511a67`. 별도 `lyricscloud_upgrade_restore` DB에 복원하고 migration을 두 번 실행했다. schema `0802 → 1151`, 기존 계정 1·곡 0·가사 0건이 유지됐다. 첫 검증 명령의 잘못된 schema 열 이름과 누락된 `NODE_ENV`는 시험 환경 오류였으며 수정 후 재실행을 인수했다.
- 기존 원본 `.env`·`.test_users`와 checkout을 바꾸지 않고 별도 private override를 준비했다. 기존 허용 주소 집합은 복사본에서 HMAC으로 이행했으며 암호화 rollback 복원본이 원본과 일치했다. runtime secret은 전용 volume에 UID 65532·0400으로 준비했다. OAuth·DB·session secret 값과 사용자 권한은 보존한다.
- 이 복구 지점은 같은 PC의 로컬 사본이다. 외부 backup·24시간 RPO·호스트 손실 복구가 검증된 것으로 기록하지 않는다.

## 미완료 인수

PC Docker 전환·최종 CI·원격 개발 동일 SHA 인수 결과는 실제 실행 후 추가한다. 현재 문서 작성만으로 이 항목을 PASS 처리하지 않는다. 원격 개발 관리 접속 설정이 아직 확보되지 않았고 실제 Google 재로그인·물리 Windows/IME/AT/서명 인수는 별도 증거가 필요하다.
