# 1.0.1 P10 최종 후보·Private Beta 릴리스 기록

## 후보 경계

P10은 [최종 요구 추적](../architecture/1.0.1-FINAL-TRACEABILITY.md), `config/migrations.1.0.1.json`, `config/environment-schema.1.0.1.json`, `config/licenses.1.0.1.json`, `config/release-manifest.1.0.1.json`을 한 후보에 고정한다. 정확한 candidate SHA, main SHA, CI run, tag object와 네 digest는 실행 뒤 이 문서와 Git 제외 운영 기록에 채운다.

P9의 unit/PostgreSQL 250 PASS, 브라우저 263 PASS·31 의도적 제외·실패 0, release matrix 10 PASS, production image·암호화 restore·upgrade/rollback·secret·취약점·관측·성능 증거를 재사용한다. P10 원격 CI는 같은 검사와 0900/0901·환경·1.0.1 artifact gate를 현재 후보에서 다시 실행한다.

## 불변 실행 순서

1. P10 branch candidate를 push하고 Draft PR과 필수 전체 CI·네 dev image 발행을 통과한다.
2. 정확한 candidate를 개발 서버에 배포해 공개 live/ready/auth·핵심 합성 smoke를 동결한다.
3. Future 검수와 P10 완료 기록을 포함한 release PR을 main에 merge하고 최종 main SHA의 전체 CI를 다시 통과한다.
4. 최종 main SHA를 개발 서버에서 재검증한 뒤 annotated `v1.0.1` tag를 같은 commit에 만든다.
5. 정확한 tag에서 `publish=true`, `release=true` 수동 workflow를 실행한다.
6. 각 서비스의 `1.0.1`·전체 SHA·`Release`·`latest`·`Release-latest`가 같은 digest인지 확인하고 signature·provenance·SBOM을 검증한다.
7. 릴리스 서버의 기존 SHA·schema·volume·설정을 읽고, release 전용 secret 경계와 exact digest compose를 확인한 뒤 migrate→세 app 순서로 upgrade한다.
8. 공개 live/ready, 기존 session, OAuth 시작/가입, 한글 저장·재진입, copy·search·export, owner 격리와 안정 구간을 합성 자료로 확인한다.

## 승인·복구 경계

사용자는 모든 Phase 완료 뒤 main·정식 이미지·릴리스 서버 배포를 승인했고, release Google OAuth와 DB 자격 증명은 개발 환경과 같은 값을 쓰도록 지시했다. 실제 값은 `.private`에만 유지하고 환경의 DB/volume·session·HMAC/beta key 파일은 분리한다.

`OPS-100-001`은 열린 승인 예외다. 배포 실패 시 직전 승인 digest로 application-first rollback하고 schema와 volume은 유지한다. 파괴적 down migration, volume 삭제, 과거 tag 이동은 금지한다.
