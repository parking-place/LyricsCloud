# 제품 버전·Phase·채널 규칙

## 최상위 원칙

**제품 메이저는 사용자 명시 지시 전까지 1이다. 기본 업데이트 단위는 패치이며, 하나의 마이너 계열을 오래 유지한다.** 기능 추가·UI 변경·플랫폼 추가는 마이너 자동 상승 사유가 아니다.

| 구성 | 사용 기준 | 금지 |
|---|---|---|
| major | 사용자가 메이저 변경을 명시 지시할 때만 검토 | 규모·기간·앱 출시를 이유로 2 이상 임의 배정 |
| minor | 권한/데이터/사용자 모델 등 제품 단계가 실질적으로 전환되고 이유·호환·인수 조건이 승인됐을 때 | 기능 종류마다 증가, 패치 횟수/자릿수로 자동 증가 |
| patch | 현재 제품 단계 안의 버그 수정·기능 추가·기능 확장·최적화·플랫폼 확장 | .9 뒤 자동 minor 증가, 빈 릴리스로 번호 채우기 |
| Phase | 한 업데이트의 계약→기반→화면→검증→인수 | Phase가 바뀔 때 제품 버전 증가 |
| 설계 ID | 디자인 조사·대안·목업·승인 | 문서/실험만으로 제품 버전·release tag 발행 |

이것은 기능 추가에도 patch를 사용하는 **프로젝트 제품 마일스톤 정책**이다. 일반적인 SemVer의 기능 추가/patch 의미와 동일하다고 설명하지 않는다. 공개 API/SDK·DB migration·CRDT wire format·OS build number는 필요한 경우 별도로 호환 버전을 관리한다. 제품 major1 고정은 데이터 단절이나 무제한 호환을 자동 승인하지 않는다.

## 현재 계획의 번호

- `1.0.x`: Private Beta와 개인 창작 공간의 점진 확장. 현재 계획은 사전·폰트를 포함한 1.0.1~1.0.14이며 필요하면 다음 가용 patch를 계속 사용한다.
- `1.1.0`: **조건부 공유 진입 후보**. owner-only에서 읽기/쓰기 주체 모델로 바뀌는 ADR·인가·복구 인수가 필요하다. 선행 검증이 없으면 승격하지 않는다.
- `1.1.x`: 공유 범위 확장, UI/UX 개선과 승인된 플랫폼 추가를 같은 계열에서 이어간다. 현재 문서는 1.1.14까지 계획한다.
- `1.1.7b`: **2026-09-23 사용자 명시 지정 — 웹 안정화 선행 통합**. [계획](../3.Redesign-phase/1.1.7.b/README.md)의 실제 인수 뒤 그 SHA에서 1.2.0을 시작한다.
- `1.2.0`: **2026-09-22 사용자 명시 지정 — Chroma Dock / Cobalt Blue 리디자인**. [3.Redesign-phase](../3.Redesign-phase/1.2.0/README.md)에 배정하고 1.1.8~1.1.14 후속 진행은 보류한다. 목업/원 리뷰 기준은 1.1.7a이고 2026-09-23 개정 이후 실제 구현은 선행 b 인수 SHA에서 시작한다. UI 변경만으로 minor를 자동 올린 것이 아니다. 그 이후 minor는 예약하지 않는다.

이 배정은 계획 번호와 실행 순서의 사용자 지정이다. 권한·데이터·프로토콜 변경을 자동 승인하지 않으며 기존 호환성을 유지한다. `VERSION`/package/runtime/발행 tag는 실제 구현·검증 단계까지 변경하지 않는다. 이유·보류 범위·이행/복구와 과거 이력 보존은 [전환 결정](../3.Redesign-phase/PLAN-CHANGE.md)을 따른다.

패치 10~30개를 **채워야 한다**는 규칙도 아니다. 목적은 숫자 할당량이 아니라 현재 제품 단계에 머물면서 작게 구현·검증하는 것이다. hotfix가 계획 번호를 먼저 쓰면 이미 발행한 tag는 그대로 두고 미착수 계획만 다음 가용 patch로 배정한다. 실제 작업 중인 문서는 담당자와 인수 후 조정한다.

## 번호를 확정하는 절차

1. 현재 배포 버전·작업 중인 버전·이미 발행된 태그를 확인한다.
2. 변경이 현재 제품 모델 안에 머무르면 다음 가용 patch를 우선한다.
3. minor 후보이면 현재 계열로 처리할 수 없는 구조적 이유, 기존 사용자/자료 호환, 이행·복구, 선행 종료 조건을 기록한다.
4. 변경의 승인·실제 검증이 끝나기 전 번호만으로 제품 단계가 완료됐다고 표시하지 않는다.
5. 계획에서 배정한 미발행 번호는 일정 약속/운영 배포 승인이 아니다. 의미 있는 제품 변경이 없으면 문서/검증 산출물로만 마감한다.
6. 각 소프트웨어 버전은 기본 5 Phase를 갖되 의존성·업무량에 따라 실제 산출물 단위로 추가할 수 있다. 1.0.1은 10 Phase다. 번호 채우기용 빈 Phase는 금지하며 이미 발행된 1.0.0 P6 이력은 보존한다.

## 형식과 정렬

**2026-09-23 추가 예외:** 사용자가 웹 안정화 선행 통합의 제품 버전을 정확히 `1.1.7b`로 지정했다. 계획폴더 `3.Redesign-phase/1.1.7.b`, private package `1.1.7` 매핑을 [버전 계약](../3.Redesign-phase/1.1.7.b/VERSION-CONTRACT.md)에 정리했다. 실제 b P1에서 a와 b만 명시적으로 지원하고 다른 접미사는 거부한다. 아래 a-only 설명은 2026-09-16 당시 승인 범위의 보존 기록이며 현재 b 계획을 거부하는 규칙으로 재사용하지 않는다. b tag/image 형식 계획은 실제 발행·별도 release branch·운영 배포 승인과 다르다.

2026-09-16 단일 사용자 예외: 이미 발행된 `v1.1.7` 뒤의 닉네임/프로필 사진·로고 홈 이동 작업 **한 번만** 제품/배포 표기 `1.1.7a`, 태그 `v1.1.7a`, Docker 불변 버전 tag `1.1.7a`를 사용한다. 계획 폴더 이름은 `1.1.7.a`다. 일반 버전 파서와 정책은 이 값만 명시적으로 허용하고 다른 문자 접미사는 거부한다. private npm package version은 SemVer 제약상 `1.1.7`을 유지하며 제품 버전과 다른 사실을 릴리스 검증에서 확인한다. 기존 `v1.1.7` 이력·tag/이미지/DB는 이동하지 않는다. 이 예외는 미완료 `1.1.8`을 출시하거나 main 릴리스 절차를 자동 예외 처리하지 않는다.

`major.minor.patch`는 선행 0 없는 세 개의 비음수 정수다. 문자열 사전순·소수·자리수 이어붙이기로 비교하지 않는다. minor/patch는 한 자릿수 제한이 없다. 구현에서는 overflow가 없는 정수 파싱 또는 동등한 안전 비교를 사용한다.

```text
1.0.9 < 1.0.10 < 1.0.12 < 1.0.30 < 1.1.0
1.1.10 < 1.1.11 < 1.1.12 < 1.1.91
1.9.0 < 1.10.0 < 1.12.91 < 1.100.200
```

마지막 줄은 parser 예제이지 출시 번호 예약이 아니다.

| 용도 | 예시 |
|---|---|
| 릴리스 UI | `v1.0.1 Release` |
| 개발 UI | `v1.1.12-p3 dev` |
| 정식 Git tag | `v1.0.1` — 발행 뒤 불변 |
| Phase branch | `phase/1.0.10-p3-suno-links` |
| 작업 ID | `LC-NF-1.0.10-P3-01` |
| 설계 ID | `LC-DESIGN-UX-P3-01` |
| 고정 요구 ID | `NF-REQ-001` |

`VERSION`, package manifest/lockfile의 관련 version, 실행 STATUS, APP_VERSION, phase/channel, build SHA의 일치를 검사한다. UI와 health는 같은 신뢰 가능한 metadata를 사용하며 hostname으로 추정하지 않는다. 개발 image와 정식 태그는 [RELEASE-POLICY](RELEASE-POLICY.md)대로 분리한다.

## 완료·호환 기준

작은 patch도 원문 유실·인가 우회·잘못된 성공 저장·복원 불가를 허용하지 않는다. 라이브러리/DB major 변경은 제품 숫자를 핑계로 자동 수행하지 않는다. 서로 호환되지 않는 변화를 검증 없이 patch로 숨기지 말고 protocol 병행 또는 사용자 승인 이행을 먼저 설계한다.

현행 `scripts/release-phase-state.mjs`는 1.0.0 P5/P6 기준이다. 위 1.0.1 P1~P10·가변 Phase·새 경로·다자리 숫자/표시/정식 alias 검증은 [1.0.1 P8](1.0.1/8phase.md)의 구현 과제이며 이 정책 문서만으로 지원 완료가 아니다.
