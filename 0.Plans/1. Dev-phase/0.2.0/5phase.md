# 0.2.0 Phase 5 — 04 기본 곡 대시보드와 곡 흐름 검증

- 상태: **대기**
- 버전 상태: [../STATUS.md](../STATUS.md)

## 목표

곡을 열었을 때 현재 상태와 기본 정보, 아직 없는 가사·연결 자료의 정직한 빈 상태를 PC와 모바일에서 제공한다. 목록→생성→대시보드→수정→삭제 흐름을 통합 검증한다.

## 선행조건

- 0.0.0의 관련 ADR이 모두 Accepted 상태이며 이 Phase는 승인 결과를 따라야 한다.
- 0.2.0 Phase 1부터 Phase 4까지의 schema, 명령, 목록, 폼이 완료되어야 한다.
- 곡 대시보드 기본 집계 응답이 준비되어야 한다.

## 작업 체크리스트

- [ ] LC-020-P5-01 — PC 대시보드에 곡 헤더, 요약 수치, 가사 빈 영역, 메모·연결 자료 빈 보조 열을 배치한다.
- [ ] LC-020-P5-02 — 모바일 대시보드에 상태·수치 요약 뒤 가사, 연결 자료, 메모를 세로 순서로 배치한다.
- [ ] LC-020-P5-03 — lyric_count, prompt_count, rhyme_count를 API 값으로 표시하고 미지원 데이터는 0과 빈 상태로 나타낸다.
- [ ] LC-020-P5-04 — 수정 행동을 03-song-form의 해당 곡 mode와 연결한다.
- [ ] LC-020-P5-05 — pin·favorite 변경을 즉시 반영하되 실패하면 서버 값으로 되돌리고 이유를 알린다.
- [ ] LC-020-P5-06 — 삭제 확인에 실제 곡 제목과 가사가 생긴 뒤 함께 숨겨진다는 영향을 표시한다.
- [ ] LC-020-P5-07 — soft delete 성공 후 삭제된 상세 route를 남기지 않고 이전 목록 상태로 돌아간다.
- [ ] LC-020-P5-08 — 첫 가사 CTA는 0.3.0 route가 연결되기 전 무반응 요소로 표시하지 않는다.
- [ ] LC-020-P5-09 — 목록→새 곡→대시보드→수정→목록 반영→삭제의 PC·모바일 E2E를 작성한다.
- [ ] LC-020-P5-10 — 사용자 B가 상세 URL과 삭제 명령으로 사용자 A의 곡 제목·존재를 확인하지 못하게 검증한다.

## 검증 방법

- 새 곡, 메모가 긴 곡, 모든 상태·색상 조합을 PC와 모바일에서 확인한다.
- 생성·수정·pin·favorite 후 목록과 대시보드가 같은 값을 표시하는지 확인한다.
- API 지연·실패 중 낙관적 UI가 잘못된 성공 상태로 남지 않는지 확인한다.
- 삭제 취소·확정·중복 요청과 삭제 뒤 직접 URL 재접근을 검증한다.
- 1440px과 390×844에서 빈 상태 CTA, 메모, 요약 카드가 겹치지 않는지 확인한다.
- 전체 E2E 뒤 DB에 orphan resource 또는 orphan song이 없는지 확인한다.

## 완료 조건

- [ ] 04-song-dashboard의 기본 PC·모바일 화면이 함께 완성됐다.
- [ ] 목록·폼·대시보드의 곡 데이터가 일관된다.
- [ ] 빈 수치와 미구현 기능을 실제 자료처럼 표시하지 않는다.
- [ ] 곡 soft delete와 목록 복귀가 안전하다.
- [ ] 전체 곡 흐름 E2E와 교차 계정 테스트가 통과한다.
- [ ] 0.3.0이 연결할 가사 영역 계약이 문서화됐다.
