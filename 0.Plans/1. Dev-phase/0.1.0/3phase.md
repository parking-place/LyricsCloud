# 0.1.0 Phase 3 — 개인 데이터 소유권과 접근 차단

- 상태: **완료**
- 버전 상태: [../STATUS.md](../STATUS.md)

## 목표

모든 향후 자료가 한 명의 내부 사용자에게 명시적으로 귀속되고, URL이나 요청 본문에 다른 사용자의 ID를 넣어도 조회·변경할 수 없는 개인 데이터 경계를 데이터베이스와 애플리케이션 양쪽에 만든다.

## 선행조건

- 0.1.0 Phase 2에서 검증된 내부 사용자 context를 제공해야 한다.
- 데이터 접근·transaction·RLS 관련 ADR이 Accepted 상태여야 한다.

## 포함 범위

- profile과 계정 활성 상태
- 모든 사용자 소유 테이블이 따를 owner_id 규약
- 요청 context에서 DB transaction으로 사용자 ID를 전달하는 방식
- PostgreSQL RLS 또는 Accepted ADR의 동등한 DB 방어선
- 애플리케이션 서비스의 owner 조건 강제
- 인증되지 않은 요청과 다른 사용자의 자료 요청에 대한 비노출 응답
- 두 사용자 교차 접근 자동 테스트
- 로그아웃·계정 변경 때 계정별 클라이언트 캐시를 분리할 계약

- [x] LC-010-P3-02 — 사용자 소유 테이블의 owner_id NOT NULL, index, 삭제 시 처리 규칙을 migration 기준으로 만든다.
- [x] LC-010-P3-03 — 인증 context의 사용자 ID를 한 transaction 안에서만 DB 정책에 전달하고 연결 풀에 남지 않게 한다.
- [x] LC-010-P3-04 — 조회·생성·수정·삭제마다 현재 owner 조건을 강제하는 공통 데이터 접근 계약을 만든다.
- [x] LC-010-P3-05 — 사용자가 요청 본문에 owner_id를 보내도 서버가 이를 신뢰하거나 그대로 저장하지 않게 한다.
- [x] LC-010-P3-06 — 다른 사용자의 존재를 추측하지 못하도록 미소유 자료 응답을 일관되게 정의한다.
- [x] LC-010-P3-07 — 사용자 A와 B의 세션·자료 fixture를 만들고 모든 작업의 교차 접근을 거부하는 테스트를 작성한다.
- [x] LC-010-P3-08 — 계정 ID별 브라우저 캐시 namespace와 로그아웃 시 제거 이벤트 계약을 정한다.
- [x] LC-010-P3-09 — 사용자 이메일과 창작물 본문을 접근 거부 로그에 기록하지 않는다.

## 검증 방법

- A로 생성한 fixture ID를 B의 path, query, body에 넣어 조회·수정·삭제가 모두 실패하는지 확인한다.
- 인증 context 없이 DB 정책이 기본 거부 상태인지 확인한다.
- 연결 풀에서 A transaction 직후 B transaction을 실행해 사용자 context가 섞이지 않는지 반복 검증한다.
- 클라이언트가 owner_id를 변조해도 저장 결과가 서버의 내부 사용자 ID인지 확인한다.
- 비활성 profile의 세션이 보호 route와 데이터 작업에 사용되지 못하는지 확인한다.
- 로그에 상대 사용자의 존재, 이메일, 제목이 노출되지 않는지 확인한다.
