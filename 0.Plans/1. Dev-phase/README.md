# LyricsCloud 개발 단계 로드맵

이 디렉터리는 [`Sketch.md`](../Sketch.md), [`Mock-up`](../Mock-up/README.md), [`Implementation-Stack.md`](../Implementation-Stack.md)를 실제 구현 순서로 연결합니다. `0.0.0`에서 개발 기준을 고정하고, 내부 마일스톤인 `0.x.x`를 순서대로 통과한 뒤, 기획된 1차 출시 범위를 `1.0.0`에서 공개합니다.

## 선택된 구현 기준의 해석

계획 작성 시 확인한 13개 `DEC`는 모두 한 항목씩 선택되어 있고 `FINAL-APPROVAL`도 체크되어 있습니다.

| 결정 | 계획에 반영한 결과 |
|---|---|
| DEC-01-D, DEC-10-C | Node.js + PostgreSQL을 먼저 로컬 Docker에서 개발하고 이후 홈랩으로 이관 가능한 형태로 자체 운영합니다. 웹·실시간 연결·예약 작업의 프로세스 경계와 프록시는 `0.0.0` ADR에서 고정합니다. |
| DEC-02-A | 1.0은 개인 계정 중심 비공개·초대 베타입니다. 팀·공유 권한 모델은 만들지 않습니다. |
| DEC-03-A | CodeMirror 6을 사용하고 가사 원본은 UTF-8 순수 텍스트입니다. |
| DEC-04-A | 설치 가능한 온라인 우선 PWA를 제공하며 미전송 초안을 계정별 로컬 저장소에서 복구합니다. |
| DEC-05-A | PostgreSQL에서 제목·본문·태그의 정확·부분 문자열 검색을 제공합니다. |
| DEC-06-C | 현재 계획 해석은 같은 소유자의 여러 기기·탭에서 CRDT/OT 계열 자동 병합을 제공하고 다른 사용자 공동 편집·공유를 제외하는 것입니다. `ADR-0004` 승인 전에는 확정 구현으로 보지 않습니다. |
| DEC-07-A | 편집 중 5분 간격과 이탈·복원·복제·대규모 붙여넣기 전에 snapshot을 만들고 180일·항목당 200개 한도를 적용합니다. |
| DEC-08-A | 휴지통 자료는 삭제 후 30일에 완전 삭제합니다. |
| DEC-09-A | 탈퇴 즉시 접근을 막고 7일 동안 철회할 수 있게 한 뒤 완전 삭제합니다. |
| DEC-11-A | 오류·성능만 수집하고 창작물 제목·본문·태그는 제거합니다. |
| DEC-12-A | 하루 1회 암호화된 별도 논리 백업과 24시간 목표 손실 범위를 준비합니다. |
| DEC-13-A | 전체 자료를 TXT/Markdown + JSON 묶음으로 내보냅니다. |

`Implementation-Stack.md`의 권장 기술 표는 `DEC-01-A` 전제이므로 자체 운영 선택에 그대로 적용하지 않습니다. 인증·세션, DB 접근·migration, CRDT transport·영속화, PWA, 백업, 관측, 프록시의 구체 제품은 `0.0.0`에서 ADR로 승인한 뒤 package manifest와 Docker 설정에 반영합니다.

|---|---|---|---|

| [`0.1.0`](./0.1.0/1phase.md) | 실행 기반·인증·앱 셸 | Google 로그인 후 개인 작업 공간의 PC·모바일 공통 내비에 진입 | 0.0.0 |

## 버전 의존 흐름

```text
0.0.0 기준·ADR·개발 환경
  ↓
0.1.0 인증·개인 데이터 경계·공통 셸
  ↓
0.2.0 곡과 공통 resource
  ↓
0.3.0 가사 편집 ─→ 0.3.1 CRDT·로컬 초안·revision
  ↓
0.4.0 라임 ─→ 0.5.0 프롬프트
  ↓
0.6.0 곡 중심 통합·우측 패널·빠른 추가
  ↓
0.7.0 검색·최근·즐겨찾기·핀
  ↓
0.8.0 템플릿·설정·휴지통·내보내기·탈퇴
  ↓
0.9.0 PWA·모바일·접근성 마감
  ↓
0.9.1 RC·보안·성능·백업·운영
  ↓
1.0.0 정식 릴리즈
```

공통 resource, 소유권과 soft delete는 `0.2.0`에서 먼저 설계하고, revision 식별자와 보존 계약은 편집 안전성을 다루는 `0.3.1`에서 설계합니다. 해당 사용자 화면은 위 표의 담당 버전에서 완성합니다. 화면은 최초 구현 버전부터 PC와 모바일을 함께 만들며 `0.9.0`까지 모바일을 미루지 않습니다. `0.9.0`은 실기기·태블릿·PWA·접근성의 전체 교차 검증 단계입니다.

## 다섯 Phase의 사용법

각 버전에는 정확히 `1phase.md`부터 `5phase.md`까지 있습니다.

1. `1phase`: 목표, 계약, 선행 조건, schema·상태·수용 기준을 잠급니다.
2. `2phase`: 해당 버전의 핵심 도메인·서버·기반 동작을 만듭니다.
3. `3phase`: PC·모바일 화면과 나머지 기능을 연결해 사용자 흐름을 완성합니다.
4. `4phase`: 자동·수동·실패·권한·회귀 검증을 수행하고 결함을 수정합니다.
5. `5phase`: 완료 조건, 문서·운영 영향, 인계를 확인하고 다음 버전 진입을 승인합니다.

각 Phase를 시작할 때:

1. 이전 Phase의 완료 체크와 산출물을 확인합니다.
2. `STATUS.md` 활성 작업 표에 담당자와 파일 범위를 씁니다.
3. 작업 ID를 Issue·브랜치·PR에 사용합니다.
4. 체크리스트 범위만 구현합니다.
5. 검증 증거와 미완료 항목을 기록합니다.

완료 조건 일부만 충족한 상태에서는 다음 Phase로 이동하지 않습니다. 일정 때문에 미룬 항목은 완료로 처리하지 않고 범위 변경 승인을 받은 뒤 추적표와 관련 문서를 함께 고칩니다.

## 전 버전 공통 품질 문턱

- 사용자 A가 사용자 B의 ID를 알아도 어떤 자료·검색·실시간 문서에도 접근할 수 없습니다.
- 가사·라임·프롬프트 본문과 Google 토큰이 로그·오류·분석 정보에 포함되지 않습니다.
- 생성·복제·저장 재시도로 중복 자료나 오래된 덮어쓰기가 생기지 않습니다.
- 화면 최초 구현부터 PC와 390px급 모바일의 정상·빈·오류 상태를 확인합니다.
- 한글 IME, 키보드만 사용, 보이는 focus, 색상 외 상태 표현을 기능별로 확인합니다.
- DB 변경에는 migration과 깨끗한 DB 재적용 검증이 있습니다.
- 수행하지 못한 테스트는 통과로 기록하지 않습니다.

## 1.0.0 완료 정의

- [`Requirements-Traceability.md`](./Requirements-Traceability.md)의 모든 1.0 항목이 구현·검증됨으로 표시됩니다.
- 15개 화면의 PC·모바일 핵심 흐름과 목업에서 보이지 않았던 필수 상태가 동작합니다.
- 치명적·높음 우선순위 알려진 결함이 0개이며, 중간 우선순위 결함은 우회 방법과 후속 계획이 승인되어 있습니다.
- 자체 운영 신규 환경에서 문서만으로 설치, migration, HTTPS·WebSocket 연결, smoke test가 재현됩니다.
- 암호화 백업을 별도 환경에 복원하고 검색용 평문과 CRDT 문서를 재검증했습니다.
- 30일 휴지통, 7일 탈퇴 유예, 전체 내보내기, 창작물 비수집 관측 정책을 검증했습니다.
- release artifact와 DB schema version을 고정하고 rollback 조건을 문서화했습니다.
